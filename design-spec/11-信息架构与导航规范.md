# 11 · 信息架构与导航规范（中后台通用 + 哈尼项目落地）

> 回答三个问题：菜单怎么组织才标准？界面应该有哪些东西？代码放哪里？
> 与 01-09 的关系：那份管"长相"（皮肤），这份管"骨架的组织方式"，项目结构管"代码放哪"。

---

## 0 · 三层模型（先分清再动手）

| 层 | 管什么 | 载体 | 改动影响 |
|---|---|---|---|
| 设计规范 | 颜色、字体、间距、组件长相 | tokens.css / antd theme | 全站视觉，一行生效 |
| **信息架构 + 导航** | **分几个组、每组叫什么、页面怎么摆、菜单怎么交互** | **菜单/路由配置文件** | 用户"找东西"的效率 |
| 项目结构 | 代码文件怎么分目录、新代码放哪 | 目录约定 | 开发维护效率 |

三者独立演化，互不牵连。换导航形态不用动设计规范；调整目录不用动界面。

---

## 1 · 菜单即配置（Single Source of Truth）

**核心原则：菜单不许散落在布局组件里硬编码。** 全站只有一份类型化的配置文件描述导航树，布局组件（ProLayout / 自研侧栏）只负责渲染它。改菜单 = 改配置，不改代码。

### 1.1 标准配置文件模板（TypeScript）

```ts
// src/config/navigation.ts —— 全站唯一菜单事实来源
import type { IconType } from "./icons";

export interface NavPage {
  key: string;            // 唯一键，如 "users.list"
  title: string;          // 菜单显示名
  path: string;           // 路由路径，如 "/users"
  permission?: string;    // 权限码，如 "user.list.read"
  hidden?: boolean;       // 有路由但不进菜单（如详情页）
}
export interface NavSection {
  key: string;
  title: string;          // 分组名，如 "用户与主播"
  icon?: IconType;        // 只有"独立项"或需要图标时才配
  order: number;          // 排序权重，小在前
  pages: NavPage[];
}
/** 独立项：不带分组的顶层页面（如 运营概览） */
export interface NavStandalone {
  key: string;
  title: string;
  icon: IconType;
  path: string;
  order: number;
  permission?: string;
}
export type NavEntry = NavStandalone | NavSection;

export const NAVIGATION: NavEntry[] = [
  { key: "dash", title: "运营概览", icon: "chart", path: "/", order: 10 },
  { key: "users", title: "用户与主播", order: 20, pages: [
    { key: "users.list",     title: "用户列表",     path: "/users" },
    { key: "users.new",      title: "新增主播",     path: "/users/new-anchor" },
    { key: "users.reviewId", title: "实名认证审核", path: "/reviews/identity" },
    // ...
  ]},
  // ...
];
```

### 1.2 改菜单的标准流程（3 步）

1. **画树**：在纸上/文档里画出「分组 → 页面」两级树，先过一遍第 2 节的规则；
2. **改配置**：只改 `navigation.ts`（增删分组、改标题、调 `order`、配 `icon`）；
3. **核对路由与权限**：每个 `path` 在路由表里有对应页面，每个 `permission` 在角色授权里能勾到。

布局组件零改动。这就是"快速调整"的答案——**所有快捷都来自"它只是一份数据"**。

### 1.3 两种导航形态（渲染层的选择，配置不变）

| 形态 | 样子 | 适用 |
|---|---|---|
| 独立项 + 常开小标题 | 高频首页带图标置顶，分组标题灰色小字、永远展开 | 页面总数 ≤ 30、一屏能放下（哈尼当前规模，推荐） |
| 全折叠手风琴 | 每组可展开收起，带箭头 | 页面很多（40+）、用户只常去少数几组 |

切换形态只改 `buildSider()`（原型）或 ProLayout 的菜单渲染配置（真实项目），配置文件原样不动。

## 2 · IA 设计规则（菜单怎么组织才"标准协调"）

### 2.1 数量与层级

- **顶层 5–9 个**（7±2 定律）。哈尼现在 7 个，正好。
- **每组 2–8 项**。只有 1 项的组→升级为独立项（如 运营概览）；超过 8 项→按子领域拆组。
- **层级最多两级**（分组 → 页面）。三级菜单是中后台可读性杀手，用页内 Tab 代替。

### 2.2 命名规范（协调感一半来自命名）

| 对象 | 规则 | 好例子 | 坏例子 |
|---|---|---|---|
| 分组 | 领域名词，2–6 字，不带动词 | 用户与主播、财务管理 | 用户相关的、其他 |
| 页面 | 任务名词，去掉冗余动词 | 充值记录、提现审核 | 管理充值记录、查看提现 |
| 同族页面 | 共用前缀对齐 | 实名认证审核 / 主播认证审核 | 身份证审核 / 主播资质 |
| 操作入口 | 动词放按钮里，不放菜单里 | （菜单）动态管理 +（按钮）批量移除 | 批量移除动态（当菜单名） |

全站同一概念只用一个词：审核类统一叫「××审核」，配置类统一叫「××配置」，记录类统一叫「××记录」。

### 2.3 排序原则

1. 高频压倒一切：最常用的组放最上（运营概览 → 用户与主播 → 通话 → 财务）；
2. 同组内按业务流：录入 → 审批 → 台账；
3. 低频配置沉底：运营配置、系统管理放最后；
4. 用 `order` 数值显式声明（10、20、30…留间隙方便插入），不要靠数组顺序。

### 2.4 每个菜单项的完备性检查

- 有唯一 `path`（能直达、能收藏、能传参跳转）；
- 有唯一 `key`（面包屑、收藏、最近访问都靠它）；
- 有 `permission`（哪怕暂无 RBAC，先留码位）；
- 详情类页面 `hidden: true`，不占菜单位。

## 3 · 界面应该有什么：标准页面类型清单

中后台 95% 的页面落在这 10 种页型里。新页面对号入座，不发明新布局。

| # | 页型 | 标准区块 | 哈尼对应 |
|---|---|---|---|
| 1 | 仪表盘 | KPI 卡区 → 次级指标卡 → 图表区 → 待办区 | 运营概览 |
| 2 | 列表页 | 工具栏（标题+主操作）→ 筛选卡 → 表格 → 分页 | 用户列表、充值记录 |
| 3 | 审核列表页 | 列表页 + 状态统计条 + 提示 Alert + 通过/拒绝 | 实名认证审核、提现审核 |
| 4 | 表单页 | 分组表单（分节标题）→ 上传区 → 操作理由 → 提交/重置 | 新增主播、业务规则配置 |
| 5 | 详情页 | 头部（标识+状态+主操作）→ 描述列表 → 关联记录 Tab | （建议补：用户详情） |
| 6 | 配置页 | 表单卡或 描述列表+编辑 | 充值档位、上传限制 |
| 7 | 双/多表面页 | 统计条 + 多个同构表格 | 主播收益、会话对账 |
| 8 | 登录页 | 居中玻璃卡：品牌 → 账号密码 → 主按钮 | 登录 |
| 9 | 异常页 | 403 / 404 / 500，插图中字 + 返回按钮 | （建议补） |
| 10 | 空状态 | 空插图 + 一句话 + 引导按钮 | 表格空态 |

**业务域 → 页面配方**（判断"该有哪些页面"的推导法）：

每个业务域通常需要：`列表`（必有）→ `审核流?`（有人工审批就加）→ `表单/配置?`（有运营设置就加）→ `详情?`（列表行点进去看什么）→ `记录/台账?`（有钱流就加）。

以「提现」域为例：列表（提现审核）+ 统计条 + 台账（收益台账里的提现出账）——不需要详情页就不硬造。

## 4 · 权限与菜单（RBAC 驱动）

- 权限码命名：`域.资源.动作`，如 `finance.withdraw.approve`、`user.list.read`。
- 菜单显隐 = 当前角色权限集合 ∩ 页面 `permission`；分组内全部不可见则整组隐藏。
- 空组比越权可见更安全：拿不准就藏。
- 操作级权限（页面里的按钮）与菜单级用同一套码，前端只做显隐，后端才是真闸门。

## 5 · 项目结构标准（domain-module 布局）

按业务域分模块，而不是按技术分层堆大目录。哈尼已有的 `modules/admin-*` 靠拢这个方向，收敛成：

```
src/
├── config/
│   └── navigation.ts        # 唯一菜单配置（第 1 节）
├── routes/                  # 路由表：path → 页面组件，与 navigation 一一对应
├── modules/                 # 按业务域一个模块，域内自治
│   ├── users/               # 用户与主播域
│   │   ├── pages/           # 该域的页面组件（列表/表单/审核）
│   │   ├── components/      # 仅本域用的组件
│   │   └── api.ts           # 本域接口封装
│   ├── finance/
│   ├── content/
│   └── system/
├── components/              # 跨域共用组件（表格封装、上传、审计理由输入）
├── theme/                   # 设计规范落地：tokens.css、antd theme、patch 样式
└── utils/
```

**放置规则（新代码放哪，一句话判断）**：
- 只有一个域用 → `modules/<域>/`；
- 两个域以上要用 → `components/` 或 `utils/`；
- 是长相/主题 → `theme/`；
- 是菜单/路由 → `config/navigation.ts` / `routes/`。

**命名规则**：模块目录 = 域名（users）；页面文件 = 页型后缀（`list.tsx` `review.tsx` `form.tsx`）；组件 PascalCase；一个模块不放另一个模块的 import（跨域只走 `components/` / 公共 api）。

## 6 · 快速自查清单（每次调菜单过一遍）

- [ ] 顶层分组 5–9 个，无单页组
- [ ] 每组 2–8 项，超了拆、缺了并
- [ ] 层级只有两级，没有三级菜单
- [ ] 分组全是领域名词，页面全是任务名词
- [ ] 同族页面命名对齐（××审核 / ××记录 / ××配置）
- [ ] 排序 = 高频优先、配置沉底，`order` 显式声明
- [ ] 每项有唯一 key / path / permission
- [ ] 详情页 hidden，不占菜单位
- [ ] 新页面能对号入座 10 种页型之一
- [ ] 权限码 域.资源.动作，角色授权页能勾到
- [ ] 新代码按"一句话放置规则"归位
