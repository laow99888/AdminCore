# Webhook 与 Twilio 短信渠道

本批为已有版本化通知模板增加 `webhook` 和 `sms`，默认关闭。继续使用每位收件人、每种渠道一条投递、数据库 Outbox、最多五次、24 小时有效期、发送权限/会话/收件人/模板重新检查及安全审计。请求只提交既有用户 UUID 与渠道名，不能提交目标 URL、手机号、密钥或供应商函数名。

## 部署配置与启用

统一 Django 配置 `NOTIFICATION_EXTERNAL_CHANNELS`，默认 `{}`。部署侧应从受保护环境变量解析 JSON，解析失败及启用但缺字段时拒绝启动，不打印配置内容。以下仅是配置结构，示例凭据不能用于真实服务：

```json
{
  "webhook": {
    "enabled": false,
    "url": "https://hooks.example.com/admincore/events",
    "active_key": "v1",
    "keys": {"v1": "replace-with-at-least-32-bytes-of-random-secret"}
  },
  "sms": {
    "enabled": false,
    "account_sid": "AC00000000000000000000000000000000",
    "auth_token": "replace-with-real-twilio-auth-token",
    "from": "+14155550101",
    "recipients": {"00000000-0000-0000-0000-000000000001": "+14155550102"}
  }
}
```

`enabled` 必须为 JSON 布尔值。启用短信要求 PostgreSQL。`recipients` 是部署管理员在线下完成号码归属、通知许可核验后登记的用户 UUID → E.164 号码映射，最多一万条；不自动使用用户自填、未验证的 `phone`，不声称已经提供手机验证码验证。号码及令牌只在受保护部署配置和 TLS 请求中使用，不进入投递记录、审计或 Outbox。模板正文为短信内容，限制 1～1600 字符；发送费用、分段和目的地合规由运营方确认。短信状态 `succeeded` 表示 Twilio API 接收，不代表手机送达；目前无入站状态回调。

## 出站与目标固定

Webhook 只接受运维配置的单一 HTTPS 443 地址，拒绝用户信息、查询字符串、片段、控制字符和非 ASCII 主机/路径。Twilio 固定为 `api.twilio.com/2010-04-01/Accounts/{AccountSid}/Messages.json`，使用官方的 Basic 身份认证与表单编码。

每次投递重新解析 DNS，所有解析结果都必须为公网 IP；任一私网、回环、链路本地、保留或混合答案立即拒绝。连接固定已验证 IP，并保留原域名的 SNI 和证书验证；不读取系统 HTTP 代理，不跟随重定向，不读供应商响应正文。DNS 最多两个并发解析、等待 3 秒；连接与读操作超时 5 秒，额外定时关闭连接防止响应头缓慢滴流。接收端仍应实施出站网络层白名单。

登记时保存目标指纹而非原地址。Webhook URL、短信账号、发送号或收件号改变后，旧任务终止，不发送到新目标。短信关闭、号码移除、人员停用或发送权限撤销也会在实际发送前终止。凭据轮换不改变目标指纹。

## Webhook 协议与接收端义务

JSON 字段：`id`（稳定投递 UUID）、`recipient_id`、`template`、`revision`、`subject`、`body`。签名为 `HMAC-SHA256(key, ascii(timestamp) + "." + 原始请求正文)`。

头部为 `X-AdminCore-Key-Id`、`X-AdminCore-Timestamp`、`X-AdminCore-Event-Id` 与 `X-AdminCore-Signature: sha256=<hex>`。最多保留三把 32～256 字节密钥。轮换时先让接收端同时接受新旧 key id，再切换发送端 `active_key`，等候在途请求结束后移除旧密钥。

`verify_webhook()` 是可复用接收端辅助函数，验证原始正文、签名、五分钟时间窗口、正文 id/头部 id 一致性，并用共享缓存原子登记 601 秒防重放标记。生产接收端不得使用进程内缓存，也必须另外使用数据库按投递 UUID 持久幂等。已持久处理的同 UUID 重送应返回 2xx；不能把合法重试重复执行，也不能把已成功的重复请求一律返回永久拒绝。辅助函数返回 False 不能单独区分“已处理重复”和“签名非法”，接收端应结合持久事件状态处理。接收端必须先可靠记录再应答；不提供任意 URL 入站代理。

2xx 视为对端接收；429、5xx 与网络异常按既有 Outbox 退避；3xx 和其他 4xx 永久终止。网络重试可能发生重复请求，接收端持久幂等是必需条件。

## 短信不确定结果与持久屏障

[Twilio 官方 Messages API](https://www.twilio.com/docs/messaging/api/message-resource) 规定创建请求采用表单 POST；201 表示创建成功，其后仍有 queued/sent/delivered 等状态。该接口文档没有承诺创建请求的幂等键，因此本实现不能靠本地重试宣称短信恰好发送一次。

每次首次发送前，另开 PostgreSQL 连接，以自动提交写入无外键的 `SmsDispatchFence`（只含投递 UUID 和时间）。独立连接有 2 秒等锁与 3 秒 SQL 限额。写入失败则禁止外发。外层 Outbox 事务回滚或 worker 退出不能抹除屏障；恢复发现已有屏障即终止为 `external_delivery_rejected_or_unknown`，不再调用供应商。

只有发送前 DNS 失败、明确 429 拒绝会释放该次屏障以允许退避。断线、超时、5xx、3xx、其他非 201 状态保留屏障并终止。代价是写入意图后、实际发出前崩溃也需要人工对账；系统优先避免重复计费。终止记录不能通过“重试”按钮绕过，运营方核对供应商记录后，确需发送时新建投递。备份恢复必须同时恢复此表；恢复到短信发送前的旧备份存在重复风险，应先停用渠道并对账。屏障目前随业务记录保留，批量归档/清理需单独按投递过期和审计保留策略安排，不能提前清除有效投递的屏障。

日志与接口仅返回受控错误代码，不记录供应商原始错误、正文、手机号、Authorization 或签名密钥。站内/SMTP 的既有行为保留。

## 验证与边界

独立单测：

```powershell
cd backend
./venv/Scripts/python.exe -X utf8 -m pytest tests/test_external_message_channels.py tests/test_message_templates.py -o addopts='' -q
```

当前 **63 项通过**，覆盖 URL/DNS/私网混合答案拒绝、固定 IP/证书主机名、真实本地 TLS 成功及错误主机证书拒绝、签名轮换/篡改/时间窗/重放、Twilio 请求协议、明确失败与不确定结果、完整批次回滚、目标变化终止、有限重试及隐私边界。SQLite 的短信屏障使用专门标明的替身，不能据此声称 PostgreSQL 持久屏障已验收。

`scripts/validate_external_channels.py` 只允许数据库名 `foundation` 且 PostgreSQL。它启动随机端口的本地真实 TLS 服务，用临时可信 CA 和两个测试域名验证实际 HTTP 请求/签名、Webhook 503、Twilio 协议 429/201，以及外层事务回滚后独立屏障仍保留、恢复不重复 POST；另以真实子进程在本地 TLS 201 后执行 `os._exit(91)`，验证恢复派发不重复 POST。脚本只在自身夹具上下文替换 DNS/连接端口和可信 CA；生产代码不存在跳过证书或放开私网开关。结束关闭服务/线程并清理随机端口、证书、仅自身 UUID 的屏障，模板/投递/事件事务回滚。需要由主验收器在隔离容器运行后登记实际结果。

上述真实 PostgreSQL/TLS/硬退出脚本已在独立 PostgreSQL 18.6 通过 **6 项**；包含进程在本地 TLS 201 后硬退出、恢复不再 POST 的实际检查。完整基础验收 **338 项通过**，证据为 `.codex-validation/admincore-foundation-32b74e71/report.json` 与同目录 `docker.log`。测试服务、临时 CA 及自身屏障已清理，正式供应商未调用。

本批没有向真实供应商发短信，没有证明真实号码送达；本地 TLS 夹具也不能替代公网 DNS、外部防火墙、真实账号额度或目的地合规验收。
