# 图片处理容量基线

2026-10-17，在隔离 PostgreSQL/Nginx/Gunicorn 中完成图片资源和并发观测。两种 worker 模式合计 **96 次变换全部成功**，原件保持完整，无 OOM 或容器重启。该结果只覆盖下面定义的合成负载和资源配置；目标项目的真实照片、水印、存储延迟、并发业务和生产 SLA 仍需独立验收。

## 可重复入口与配置

Windows：`backend/venv/Scripts/python.exe scripts/validate_images.py`；已安装项目开发锁依赖的 CI/Linux：`python scripts/validate_images.py`。需要 Docker Compose、Node 和 Playwright Chromium，18460/18461 空闲。脚本使用随机项目名、独立数据库 `images_fixture`、合成媒体及临时强密码，不连接既有业务库或站点。

只对本次隔离后端设置 1 CPU、1536 MiB，通过 cgroup `cpu.max`/`memory.max` 及实际 Gunicorn 参数复核。先运行精简预设的 1 进程/4 线程，再重建为部署默认的 3 个同步 worker。后者验证相同图片路径在同步 worker 中的表现，未启动完整预设的其他业务服务。测试限制没有写入默认生产 Compose。

每个模式单独创建四个身份和四个原件：4000×4000（1600 万像素）的合成灰度渐变 JPEG，源质量 90；变换为 2000×2000 WebP，质量 80。源图压缩率高，本轮不代表高熵照片的最坏编码 CPU 时间。分别以 1、2、4 并发访问不同账号/原件，以及四并发访问同一账号/原件，每阶段 12 次请求。不同账号场景避免用户行锁串行化掩盖解码内存的并发峰值；同账号场景保留现有锁和及时撤权语义。

## 最终实测

证据项目：`admincore-images-63919bce`。下表延迟从客户端发起 POST 开始，至读完响应并完成图片解码校验；不是单独的服务端处理耗时。每阶段只有 12 个样本，使用 nearest-rank，**p95 等于该阶段最大值**，不能作为稳定的生产分位数估计。

| 模式 | 并发/身份 | 吞吐（次/秒） | p95（毫秒） | 内存累计峰值（MiB） |
| --- | --- | ---: | ---: | ---: |
| 1 进程/4 线程 | 1，不同账号 | 1.099 | 1298.83 | 405.3 |
| 1 进程/4 线程 | 2，不同账号 | 1.186 | 2046.04 | 643.4 |
| 1 进程/4 线程 | 4，不同账号 | 1.160 | 3703.98 | 900.0 |
| 1 进程/4 线程 | 4，同账号/原件 | 1.286 | 3139.86 | 900.0 |
| 3 个同步 worker | 1，不同账号 | 1.068 | 1309.95 | 539.9 |
| 3 个同步 worker | 2，不同账号 | 1.182 | 1988.18 | 736.4 |
| 3 个同步 worker | 4，不同账号 | 1.135 | 5105.77 | 827.9 |
| 3 个同步 worker | 4，同账号/原件 | 1.178 | 3487.62 | 827.9 |

精确值以 `capacity-threaded-report.json`、`capacity-sync-report.json` 为准。内存是该容器 cgroup 自启动以来的累计峰值，包含页缓存和观察进程，不能当成单请求或单 worker RSS；不同阶段没有重置峰值。每次切换模式会重建容器，因此两种模式拥有各自的累计统计。报告还保留内存当前值、上限、memory.events、CPU 使用及限流计数、容器状态和启动参数。

这组 1 CPU 负载中，增加并发后的吞吐提升很小，等待时间明显增加。容量配置应同时考虑像素上限、实际内容和并发，不能按上传 JPEG 的压缩大小估计解码内存，也不能从本表推出固定用户数上限。本轮没有放宽授权锁、像素/字节边界或撤权检查。

## 验收门禁与证据

每个 200 响应都实际解码，验证 WebP、2000×2000 和私有禁止缓存头；请求错误、假图片、OOM 或容器重启均使验收失败，并停止后续压力阶段。单请求连接/读取超时为 5/20 秒；没有据此宣称业务满足某个 p95 SLA。阶段报告逐步落盘，失败保留日志与隔离诊断资源。容量后再次核对原件完整，使用真实 refresh 轮换进入功能关闭/恢复验收，保持 access 五分钟有效期。

`scripts/tests/test_image_capacity.py` 的五种正反例验证成功、HTTP 错误、损坏图片、OOM 和重启；连同已有 HTTP 性能门禁反例共 10 项通过。真实验收继续包含桌面/手机登录、变换、水印、下载、草稿守卫，以及 PostgreSQL 锁等待后账号/设备/权限/范围/版本/删除复核。严格 OpenAPI 也通过。

GitHub `images` 作业运行反例检查和同一真实脚本，上传总报告、两个容量报告和安全命令日志；Docker inspect 只读取状态与固定启动参数，不导出容器环境。成功清理本项目容器、卷、临时镜像标签和凭据，保留报告；失败保留诊断证据。共享六服务、依赖、构建缓存及用户原有文件不清理。

最终证据位于 `.codex-validation/admincore-images-63919bce/` 与 `r5-images-two-modes.log`。先前单模式基线 `8fefd203`、`70597fec` 也通过，均已清理其隔离运行资源；首轮本地日志中的临时环境字段已脱敏，后续脚本不读取完整 inspect 环境。

R5 仍包含真实项目容量拐点、SSE 长时连接及目标环境故障预算等待验收项。本记录提供可复跑的图片边界证据，不把这些外部条件记为完成。
