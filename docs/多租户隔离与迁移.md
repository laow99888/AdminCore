# 多租户隔离与迁移

多租户默认关闭，通过 `ADMINCORE_MULTI_TENANT_ENABLED=true` 启用。关闭时现有单项目数据继续可见，历史记录的 `tenant` 可以为空；启用前应先为历史记录指定归属。

## 请求与成员

- 普通用户访问业务入口必须有有效租户成员；只有一个正常租户成员时自动选中。无租户头的只读 `/api/v1/auth/me/` 与 `/api/v1/organization/my-tenants/` 是身份引导例外，用于获取账户和可选租户，不能扩大成业务入口例外。
- 用户属于多个租户时，客户端必须在请求头发送 `X-AdminCore-Tenant: <tenant UUID>`。
- `staff`/`superuser` 没有请求头时保持全局运维视图；带请求头时按该租户读写。
- 租户状态为 `suspended` 或 `closed` 时不能建立上下文；关闭租户会停用成员，不删除业务记录。
- 租户和成员管理入口为 `/api/v1/organization/tenants/` 与 `/api/v1/organization/tenant-memberships/`，仅管理员可用。

## 数据范围

继承 `apps.core.models.BaseModel` 的基座业务模型统一增加可空租户外键。请求上下文存在时，新取出的默认管理器查询会按租户过滤；视图中预先构造的类级 QuerySet 须使用 `TenantQuerysetMixin` 或在每次请求重新限定范围，不能仅靠导入时的管理器。实例 `save()` 会填入当前租户并拒绝跨租户写入，但 `QuerySet.update()`、`bulk_create()` 等绕过实例保存的写法仍须显式限定归属、校验关联和授权。源码见 [上下文](../backend/apps/core/tenancy.py) 与 [基础模型](../backend/apps/core/models.py)。后台任务在可信租户上下文中执行，并在结束时清理；迁移确需跨租户读取时使用 `all_objects`，自行维护边界。

当前租户字段覆盖基座业务记录、文件、任务记录、导入批次、通知、权限、审批、日志和示例业务。用户账号、会话等平台身份数据仍是全局资源；文件/任务/导入导出调用方必须在创建和读取时保留请求租户上下文。

## 旧库迁移

先执行预览：

```powershell
cd backend
$tenant = '替换为实际租户UUID或slug'
python manage.py assign_legacy_tenant --tenant $tenant
```

确认输出的模型和数量后显式执行：

```powershell
python manage.py assign_legacy_tenant --tenant $tenant --apply
```

命令将全部继承 BaseModel 且 `tenant IS NULL` 的记录归入同一目标，不能用于已经混合多个客户数据的库；目标租户必须处于 active，不覆盖已有归属、不创建成员。生产执行前先停写、备份并核对每个模型数量及授权关联，再明确批准 `--apply`；预览计数不是锁定快照。角色归属导致的 NULL 授权关联另按 [部署指南](部署指南.md) 的只读修复预览核查。完成迁移和成员授权后再启用开关，并重新创建读取配置的 API/worker/beat 等容器，普通 restart 不会载入 Compose 环境变更。
