# TOTP 双因素认证

本批为可选认证能力。已有账号不会自动开启；用户绑定认证器并输入有效动态码确认后生效。精简预设同样保留认证能力，不要求邮件、worker 或通知模块。

## 用户流程

在「设置 → 双因素认证」输入当前密码，取得仅本次展示的绑定密钥，在认证器中手工添加账号，再输入六位动态码完成绑定。启用后，登录需要密码和动态码，也可使用一枚恢复码。密码找回不会关闭双因素认证。

启用及重新生成恢复码时展示十枚恢复码，应立即离线妥善保存。每枚只能使用一次，重新生成会废止旧码。关闭和重新生成均需要当前密码及动态码或恢复码。启用、关闭和重生成会撤销全部旧会话，并为已完成证明的当前用户签发新会话。

动态码采用 SHA-1、六位、30 秒时间步，接受当前时间步前后一格，已用时间步不可重复使用。服务器与认证器应保持时间同步。绑定信息十分钟过期，并绑定发起设备及当时密码/会话版本；改变密码或撤销设备后须重新绑定。

## 部署与保管

安装锁定依赖后生成独立密钥：

```powershell
backend/venv/Scripts/python.exe -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

将结果仅写入部署环境的 `AUTH_TOTP_ENCRYPTION_KEY`，不要提交 Git。留空时不能新绑定；已开启账号仍要求第二因素，配置缺失或无法解密时拒绝认证。格式不合法时启动配置检查失败。JWT 的 `DJANGO_SECRET_KEY` 不能代替此密钥。

数据库保存 Fernet 加密的认证器密钥和恢复码哈希，密码、动态码、绑定密钥及恢复码不进入审计。绑定 URI 与恢复码仅在响应/页面内存中存在，不落 URL 或浏览器持久化。使用本地认证器录入，不向第三方二维码服务发送密钥。

备份数据库时，必须另行安全保存该密钥并验证恢复。数据库备份本身不能恢复认证器能力；直接换密钥会使已有设备不可解密，本批不提供批量密钥轮换界面。密钥配置权限应与数据库备份读取权限隔离。

启用用户不能通过 Django 管理后台的密码登录绕过第二因素，既有 Django 后台会话也会被阻止；日常管理通过本系统前端及受保护 API 进行。账号仅丢失认证器时可使用恢复码；两者全部丢失需由部署运维核验账号归属后执行终端恢复，例如：

```powershell
docker compose exec backend python manage.py recover_totp account --confirm-username account --reason "已核验账号归属，认证器与恢复码均丢失"
```

命令会关闭该账号的双因素、清除恢复码并撤销其全部会话，留下恢复原因审计；用户名必须精确确认，无 HTTP 恢复入口。上例仅为操作说明，本批不会替任何真实账号执行恢复或关闭认证。
