# 自动备份与恢复目标

本批交付注册备份计划、任务中心记录、受限宿主执行器、停写数据库/媒体快照、失败站内告警、完整备份保留策略以及独立私有 S3 协议副本。默认关闭，不要求小项目运行执行器。正式环境未配置独立备份目标，不能称为已具备生产异地容灾。

## 执行边界

- `tasks.request_backup` 只登记任务，应用和 Celery 不挂载 Docker socket。`BackupRequest` 保存领取令牌、领取时间和保留参数；PostgreSQL 约束使等待/执行中的备份最多一个。
- `scripts/backup_runner.py` 在受信任宿主工作区运行，默认每 30 秒领取一次。只调用固定 Compose 服务与管理命令，不接受网页传入的命令、路径、桶或凭据。
- 执行器记录原先运行的 frontend/worker/beat/backend，120 秒优雅停止后导出 `pg_dump -Fc` 与当前 Django 存储媒体，随后恢复这些服务并等待健康。既有长期任务需在维护窗口前排空；绕过应用直接写数据库/媒体的外部系统也必须停写，不能凭停 Compose 服务假定其停止。
- 文件先写 `.partial`；校验数据库归档目录、媒体普通文件路径和 SHA256，再发布 `.sha256` 与完成标记。独立副本按数据库、媒体、清单顺序上传并逐项重新读取核对；只有最终清单存在且摘要完整才视为远端备份集。
- 传输和回收发生在应用恢复后。一次执行预算 90 分钟，服务恢复额外保留时间；后台领取租约两小时。过期未领取记 `runner_unavailable`，过期运行记 `result_unknown`，不自动重做停写。进程被系统杀死或宿主断电无法执行 finally，需运维恢复服务并核对产物。
- 备份、旧人工脚本和交互恢复共用工作区宿主锁。锁只覆盖一次执行，空闲轮询时释放；避免另一个执行器、旧脚本或恢复同时切换服务。不同工作区克隆不能共享该锁，不可同时控制同一 Compose 项目。恢复前仍应关闭后台自动计划，避免恢复结束后立即登记新备份。

## 启用方式

1. 配置独立磁盘/挂载目录或专用私有 S3 桶。宿主目录默认 `backups` 便于开发；与数据库同机同盘不能应对整机损坏。
2. `.env` 设置 `ADMINCORE_BACKUP_ENABLED=True`，默认保留 30 天且至少 7 份。独立对象副本使用 `ADMINCORE_BACKUP_S3_*` 专用变量，与媒体凭据和命名空间分离。生产 HTTPS；`ALLOW_HTTP=True` 仅隔离 MinIO 测试。
3. 更新 backend/worker/beat，执行 `python manage.py configure_maintenance`。注册计划默认禁用，默认每天 Asia/Shanghai 02:00，避开 03:00 清理；命令不覆盖管理员已修改的计划。
4. 在宿主运行执行器，确认手动备份、完整副本和隔离恢复可用后，在“定时维护”启用备份计划。可以调整 cron、预览策略或立即执行；实际执行确认“执行备份”，不套用永久清理预览。

Windows（现有 Python 环境）：

```powershell
backend/venv/Scripts/python.exe scripts/backup_runner.py --backup-dir E:/AdminCoreBackups
# 交给 Windows 任务计划程序：开机触发、固定工作目录 D:/AdminCore、失败重启、禁止重复实例。
# 也可每分钟调用 --once，由数据库领取令牌与宿主锁防止重入。
```

Linux：

```bash
python3 scripts/backup_runner.py --backup-dir /mnt/backup/admincore
# systemd 使用固定 WorkingDirectory、受信任部署账户、Restart=on-failure；
# 或 cron 每分钟调用 --once。账户需已具有当前 Compose 管理权限，不为执行器额外提升权限。
```

执行器仅用 Python 标准库，宿主不需要 Django/S3 凭据；上传使用固定后端容器中的独立备份配置。备份目录限制为私有部署账户读写，完整 dump 与媒体包含业务数据，不通过 Web API 提供下载。

## 保留、失败及恢复

自动回收只处理本执行器完成标记及三个固定文件均可重新校验的备份集；同时超出天数和最少份数才删除。损坏文件、`.partial`、失败记录、人工备份及无完成标记的旧备份保留。回收异常在任务结果 `retention_warning` 展示；远端保留由专用桶生命周期配置，建议比本地更长并开启版本控制/对象锁，程序不自动删远端对象。

失败类型和任务 ID 在任务中心、启用通知模块的活动管理员站内通知中记录；通知模块关闭时仍保留任务记录。站内告警不是系统宕机时的外部监控，生产需要独立监控执行器存活、最近成功备份时间、磁盘余量与服务恢复。

将远端三个文件下载到私有恢复目录后校验清单，调用 `BACKUP_DIR` 对应的 `scripts/restore.sh <时间戳>`。自动清单使用 basename，可迁移目录；旧路径清单仍兼容。恢复脚本继续要求人工确认、隔离库验证、媒体 staging 和失败回滚，不自动覆盖正式库。Linux 使用 `python3`；Windows 执行器显式选择 Git Bash（可用 `ADMINCORE_BASH` 配置可执行路径），宿主目录使用 `D:/...` 格式，避免默认 WSL bash 无法识别 Windows 路径。人工 Bash 入口需 `ADMINCORE_PYTHON` 指向现有 Python 可执行文件，也可直接调用 Python 执行器的 `--restore`。

如果完整备份已发布但任务结果回写失败，保留 `.receipt.json`，核对完成标记和 SHA256 后通过受信任宿主 `backup_queue finish <record_id> --token <领取令牌>` 从 stdin 提交 receipt；必须在租约内，过期任务结果记未知，不能直接再次执行。领取令牌只在受信任宿主内使用，不进入前端或 Git。恢复库中的当次备份记录可能为 running，过期后记未知，这不是恢复失败。

## 恢复目标与演练计划

| 项目 | 开发基线与项目验收要求 |
|---|---|
| RPO：可接受数据丢失窗口 | 每日计划的初始目标为 24 小时；必须以最近**成功且可恢复**的备份时间计算，失败会扩大窗口。需要更小 RPO 的项目应配置更频繁窗口或 PostgreSQL WAL/PITR，本批不提供 PITR |
| RTO：恢复时间 | 初始规划目标为 2 小时，包含下载、校验、隔离恢复、媒体切换和业务验收；实际项目需用代表性容量测量后签认，微型测试不能证明生产 RTO |
| 演练频率 | 上线前、每次数据库/存储/加密密钥或重大迁移变更后执行；常规至少每季度隔离恢复，记录容量、下载/停写/恢复时间、业务核对结果与负责人 |
| 密钥保管 | JWT/Django、TOTP、手机号 Fernet、S3/SMTP 等部署配置不进入归档；密钥在与备份不同的受控位置保存并验证可取回。只恢复数据库不能解密丢失独立 key 的字段 |
| 升级和回退 | 备份前记录代码提交、数据库主版本、存储模式和迁移状态。恢复使用相匹配版本；不可把数据 dump 当作自动降级迁移。先验证兼容性再升级，旧库/媒体回滚副本在业务签认前保留 |
| 通过条件 | 三个产物/远端副本摘要一致、匿名访问被拒、隔离数据库迁移与业务记录正确、媒体可读取、登录权限与关键业务通过、RPO/RTO满足项目批准数值 |

## 2026-10-17 可选实时服务与 Tunnel 编排

SSE 服务也会维护数据库连接租约，备份和恢复须将正在运行的 realtime 纳入协调。执行器现按运行服务列表暂停并恢复它；恢复和失败回滚同样只协调原来运行的登记角色，避免向未启用的 worker/beat 发出停止命令。新增快照成功/失败和真实 Bash 恢复成功/失败四条回归，先在旧实现下复现失败，再验证修复。Bash 回归使用无数据库的 Docker 命令边界夹具，不能替代真实恢复验收。Windows 工具专项及 Linux 全量执行器测试通过；真实数据库恢复继续由既有专项及本次部署记录说明。

Tunnel 等显式编排部署可在受信任宿主环境固定 `COMPOSE_FILE`（绝对路径列表）、`COMPOSE_PATH_SEPARATOR`、`COMPOSE_PROJECT_NAME` 和 `COMPOSE_ENV_FILES`，让执行器与恢复子进程复用同一部署边界。启动前必须将 `docker compose config --format json` 的解析结果与日常包装器结果在内存中比较，不输出解析环境或凭据；不能只设置项目名而遗漏覆盖文件和私有环境。服务器已验证这一环境方式与 `/opt/admincore/compose` 完全等价；启用自动执行器、备份计划、停写与恢复演练的实际结果另见部署交付记录。
