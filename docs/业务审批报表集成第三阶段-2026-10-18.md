# 第三阶段：业务、审批与报表集成

本阶段基于第一阶段的真实业务模块生成器，接入审批中心和报表构建器。第二阶段的在线表单仍负责独立表单采集；复杂业务数据、主子表事务与业务约束保留在生成模块及其手写扩展中。

## 已实现的链路

生成业务记录 → 提交审批 → 按服务端业务字段选择条件路径 → 解析当前节点审批人 → 多级审批 → 原事务回写业务状态 → 按权限和数据范围汇总报表。

生成器的「业务配置」可以开启审批、指定已发布流程编码和标题字段，并登记报表维度、数值指标及筛选字段。不开启集成时沿用原有 CRUD。定义导入、导出、源码预览和下载保留这些配置；源码接入仍需要开发者审查、迁移和登记，不在网页上执行安装。

示例在 [examples/business-integration](../examples/business-integration)：`purchase-orders.json` 为采购主子表，`purchase-flow.json` 为金额条件及两级角色审批，`purchase-report.json` 为审批状态分组的金额汇总。先接入第一阶段示例中的供应商、分类，再接入本阶段采购单。流程中两个角色 UUID 是占位值，发布前必须替换为目标租户中的实际角色，并分配有效成员。订单合计由第一阶段文档中的 `extensions.before_save` 使用 `Decimal` 计算；示例不会把客户提交的合计当成可信金额。

## 业务状态和一致性

| 状态 | 编辑 | 删除 | 提交 / 撤回 |
| --- | --- | --- | --- |
| 草稿 | 可以 | 没有审批历史时可以 | 创建人可提交 |
| 审批中 | 禁止 | 禁止 | 创建人可撤回 |
| 已通过 | 禁止 | 禁止 | 禁止再次提交 |
| 已驳回 / 已撤回 | 可以，编辑后恢复草稿 | 有审批历史时禁止 | 创建人可重新提交 |

生成模型增加 `approval_status` 和指向审批申请的受保护外键，序列化接口只读返回。提交/撤回接口只接受 `{version}`，要求业务模块的 `submit` / `withdraw` 权限、数据可见性和创建人身份。业务列表显示状态和允许的操作，审批中心显示提交时的业务快照。

服务端从锁定业务记录读取流程输入和主从快照。客户端不能替换输入、状态或快照，也不能从普通审批创建接口伪造业务关联。审批参与人可以查看被提交的快照，即使没有业务模块读权限；这是提交人向审批参与人的显式信息交付。快照包含提交时的业务字段及明细，关系和附件保留 ID，不额外授予关联记录或文件的读取权。业务输入和快照在提交后不随原记录变化。

提交、步骤处理、撤回、结果回写、业务版本递增和审计处于数据库事务内；回写或审计失败时整体回滚。审批中心直接撤回也会同步业务。审批申请行先于业务行加锁，避免最终通过与撤回反向加锁。重复提交支持幂等键，旧版本操作返回 409。关闭业务模块会隐藏其入口和报表源，已经发起的审批仍可完成状态回写；不要在有待办时卸载源码或移除模型。

## 条件流程 V2

`schema_version: 2` 明确选择新协议，旧流程保持原有语义。V2 登记 `inputs`，支持 text / integer / decimal / boolean / date。输入必须完整匹配登记字段；业务接入按同名主表字段及类型匹配，不接受任意路径或表达式。金额为十进制字符串，用 `Decimal` 精确比较，不能提交 JSON 浮点数或指数文本。

流程包含 start、end、branch 和 user / parallel / or 审批节点。每个分支配置 2～20 个出口，恰好一个默认出口；其他出口按连线顺序匹配第一个成立条件，均未匹配走默认出口。设计器提供连线上移/下移。比较支持 eq / ne / lt / lte / gt / gte，文本及布尔仅支持 eq / ne。所有节点必须可达、无环，所有可能路径都必须经过审批节点，非分支节点只有一个出口。

人员来源支持固定人员、申请人和角色成员。角色及成员在进入该节点时解析，检查启用状态和租户成员资格；未经过的条件分支不会提前生成步骤。当前节点最多 100 人，支持 all 会签和 any 或签。初始化没有有效审批人返回 400；后续推进找不到有效审批人返回 409，并保留当前待办和未提交的步骤动作。已发布定义不可直接编辑，后续角色成员变化只影响尚未进入的动态节点。

这是一套受限的有向无环审批流程。parallel 表示同一节点多人会签，不表示多条流程令牌同时执行；本阶段不包含 BPMN 导入、并行分叉汇聚、循环、任意脚本、部门主管推导、跨租户角色或同编码多版本发布。

## 报表登记与权限

业务源只从已安装、已登记、已开启的 V2 生成模块发现。生成定义明确列出 `reports.dimensions` / `metrics` / `filters`，禁止客户端指定任意模型、关联路径、SQL 或回调。金额和整数可作为 sum / avg 指标，id 自动提供 count；维度可包含文本、枚举、字典、布尔、日期、时间和审批状态。

报表源发现与运行都要求业务模块读取权限；运行使用业务服务的可见查询，继承数据范围和租户隔离。筛选值按真实模型字段校验，金额使用十进制字符串。时间维度按当前时区截为日期。金额聚合结果以十进制字符串返回；图表绘制可能转换为显示数值，精确金额应以表格/API 结果为准。现有报表最多两个维度、三个筛选条件、100 个结果组，本阶段不提供任意跨表连接或明细表聚合。

## 接入及验收

基座新增 `approvals.0005_approvalrequest_business_binding` 迁移。已有业务模块增加审批配置后，重新生成受管理文件，保留手写扩展，再创建并审查该模块的字段迁移。按生成模块文档登记依赖、前后端入口，执行初始化并分配 read / submit / withdraw 权限，发布匹配的 V2 流程后开启使用。审批中心、通知及报表按目标环境的模块配置启用。

```powershell
# 仓库根目录；独占 PostgreSQL、生成模块与生产构建浏览器验收
python scripts/validate_codegen_v2.py --integrations --postgres --browser

# backend 目录，DJANGO_ENV=testing
python -m pytest --cov=apps --cov-fail-under=90

# frontend 目录，使用仓库固定的 Node/npm 版本
npm run test:coverage -- --maxWorkers=2
npm run test:typecheck
npm run lint
npm run sdk:check
npm run build
npm run check:bundle
```

隔离验收使用随机测试密码和独占本机端口 18471/18472，不修改共享容器、现有管理员或部署数据库。失败保留日志、截图和 trace，停止专属服务及数据库；成功清理临时源码、构建和数据库，保留依赖与报告。密码文件始终删除。CI 已增加同样的第三阶段验收步骤；远端 CI 和部署结果应以实际执行记录为准。
