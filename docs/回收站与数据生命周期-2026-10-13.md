# 回收站与可选软删除

本批交付可选择接入的 `SoftDeleteModel`、文件回收站页面/API、恢复及永久删除、保留期预览和分批清理。现有文件表原记录、存储对象键和上传者不变；新增迁移 `files.0002` 添加删除操作者、生命周期版本及过期清理索引。其他资源不能仅靠继承模型就宣称已经接入回收站。

## 用户入口与权限

`/files/recycle` 支持搜索、分页、单项/当前页批量恢复和永久删除。删除前显示所选文件数量、字节总量及逐项影响，输入 `DELETE` 后执行。批量最多 100 项，结果显示每项成功、不存在、冲突或存储失败；成功与失败分别计数，不把部分失败显示成全部成功。刷新、筛选和翻页清空选择，连续请求的旧响应不能覆盖新列表。

权限为 `file:recycle`（查看与保留期）、`file:restore`（恢复）、`file:purge`（永久删除）。每次请求重新检查有效角色；列表、恢复、影响预览及执行共用文件数据范围。普通用户默认只见本人文件；已有部门/自定义/全部范围按既有规则生效。恢复不改上传者或组织归属，关闭组织管理入口也不取消数据范围。存储文件已不存在时恢复返回 409，不创建假记录、不换绑另一份文件。

新库的运营编辑角色默认查看和恢复，系统管理员角色具备三项权限；旧库升级只登记权限，**不自动给已有角色增加回收站授权**。`is_staff`/超级管理员仍按既有通配权限访问。管理员可在角色页面按需要授权旧角色。回收站种子菜单只补录一次，之后保留管理员对它的编辑和删除。

文件回收站随 `files` 模块关闭，API、菜单、前端路由撤下，已有文件、软删除记录和审计保留；重新启用后原记录重新可见。关闭 `tasks` 时回收站仍可使用，自动清理不能运行。页面读取实际保留参数及启用的维护计划；有计划不等于 worker/beat 已运行，仍应通过部署和队列监控检查执行情况。

## API 契约与兼容

| 接口 | 契约 |
|---|---|
| `GET /api/v1/files/recycle/` | 仅已删除记录，沿用分页/搜索/筛选；返回删除时间、操作者和生命周期版本 |
| `GET /api/v1/files/recycle_policy/` | 统一响应中的 `retention_days` 与 `cleanup_enabled`（模块及数据库定时计划已启用） |
| `POST /api/v1/files/{id}/restore/` | 必填 `lifecycle_version`；成功为统一响应，陈旧版本/状态/存储缺失返回 409 |
| `POST /api/v1/files/recycle_action/` | `action=restore/purge`，`items=[{id,lifecycle_version}]`；拒绝空列表、重复 ID 或超过 100 项 |
| 永久删除预览 | `action=purge,dry_run=true`，仅查询当前可执行范围，无文件删除或成功删除审计 |
| 永久删除执行 | 同一份 ID/版本，`confirmation=DELETE`；再次检查权限、范围和版本，预览不能授权未来发生变化的记录 |

新增写接口/保留期接口采用 `{code,message,data}` 响应。既有上传接口保留原非分页响应，避免改变已有客户端。旧 `DELETE /files/{id}/purge/` 保留管理员兼容行为，可删除活跃或已删除文件，没有新增批量接口的预览/确认契约；已修复它的范围查询、并发版本复核和审计 ID。新页面只使用受单独权限和确认保护的批量接口。不能把旧 API 当作“全站敏感操作二次确认已完成”。

软删除、恢复和最终清理共用数据库行锁。恢复和永久删除持锁后复核版本；定时清理持锁后重新检查 `is_deleted` 与截止时间，不信任扫描时的快照。恢复先提交时，清理跳过该记录；清理先完成时，恢复报告不存在。相同版本的并发恢复只允许一个成功。默认 30 天，实际取已登记的系统参数/部署默认；超过保留期但尚未清理且文件存在的记录仍允许恢复，保留期不构成恢复保证。

## 清理、审计和失败处理

`tasks.cleanup_soft_deleted_files(dry_run=True,batch_size=100)` 记录预览结果（过期记录数、字节数和保留期），不删除文件。执行参数仅允许布尔 `dry_run` 和 1–100 的整数批量大小；不注册任意函数或命令。正常每日维护计划沿用原调度时间和启停选择，本次升级不在正式库手动触发清理。

执行固定截止时间、按主键游标分批处理，不一次加载全部过期记录。成功永久删除逐项记录文件 ID、前状态、操作类型及任务记录 ID；交互删除/恢复记录前后状态、操作者和请求 ID。批量实际操作另存逐项结果及成功/失败计数，失败项可刷新后重试。失败任务保留已完成数量，重跑只处理仍符合条件的记录，不能撤销已经完成的永久删除。

数据库与外部存储没有分布式事务。先持数据库锁、写事务内审计，再请求删除对象，最后删除数据库记录；明确存储失败时保留数据库记录并回滚该项成功审计。远端已删除但响应丢失、或删除后数据库提交失败，可能留下仍在回收站但对象缺失的记录：恢复返回冲突，不能承诺网络故障会还原对象；应重试清理或从备份恢复。审计不保存文件内容、密码、令牌或存储凭据。

## 新资源如何接入

1. 显式继承 `SoftDeleteModel`，生成新增迁移，评估已有表及查询索引。
2. 明确活跃列表、详情、关联选择、统计及后台任务的可见性；默认模型管理器保留全表以兼容维护用途，**不会自动隐藏已删除记录**。业务查询必须显式过滤并接入统一数据范围。
3. 写操作通过 `soft_delete(actor=...,expected_version=...)` / `restore(expected_version=...)`；禁止绕过这些方法直接更新状态。API 必须提交并复核版本、采用事务和资源审计。
4. 通过 `validate_restore()` 定义关联记录的恢复条件；不级联复活关联对象。文件上传者被删除后为 NULL，只在管理员/明确允许的范围可见；恢复不会重新创建账户。
5. 唯一字段默认继续占用。需要复用标识时，可采用活跃记录条件唯一约束；恢复调用唯一字段/模型约束验证，冲突返回明确结果，并由数据库约束防止并发竞争。
6. 实现资源自身的权限、回收站查询/页面、保留期、最终删除和测试。模型基础提供生命周期方法，不自动生成任意业务表的 API。

当前分类：文件接入本批机制；用户维持现有硬删除与账户撤销逻辑，部门采用关联保护/停用，字典采用停用，审批保留状态机。会话/幂等记录按到期和撤销处理，审计按审计保留策略处理；关联表跟随其归属。全资源统一保留配置、日志/导出/临时文件清理、自动备份调度/告警及指定会话撤销仍是清单待办，不能以本批文件清理替代。
