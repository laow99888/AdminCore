# 字段权限诊断深化

本次增加角色管理页的“字段权限诊断”，解释目标用户当前已保存的字段策略、功能权限和数据范围来源。诊断不读取业务记录和值，也不授予任何新权限。

## 使用与范围

管理员在角色列表打开诊断，输入目标用户 UUID，选择已登记的资源、字段和读取/新增/修改动作。接口为 `POST /api/v1/permissions/field-diagnostics/`，要求当前管理员身份、`role:read` 与 `user:read`；事务内重新检查操作者、设备会话和强制修改密码状态。响应禁止缓存。

多租户开启时必须先选择有效租户，目标必须为该租户有效成员。不存在与越租户用户统一返回 404；角色和范围声明使用当前租户查询。诊断不提供可枚举的用户搜索或跨租户角色名。

字段组合规则与真实字段授权共用 `resolve_field_policy`：管理员绕过字段限制；没有有效角色声明资源策略时保留旧版完整登记字段；存在声明时按有效角色字段并集计算，未声明策略的其他角色不放宽该资源。停用角色显示来源但不贡献授权。每次运行重新读取当前用户和角色，不用缓存的角色配置。

诊断先按主键顺序锁定操作者和目标用户，再锁定角色本体；角色策略编辑使用相同角色锁，避免一次说明混用旧字段策略和新功能权限。这里仅验证 SQLite 行为，PostgreSQL 并发仍需整合验收。

功能权限检查使用资源对应的粗粒度权限码、用户状态、模块开关和已知管理员门槛。角色新增对应 `role:update`，岗位所有操作要求管理员，文件/日志/任务不提供通用元数据写入入口。显式业务资源只使用同资源在模块契约登记的动作权限。

## 明确边界

- `field_allowed` 只说明字段策略，`operation_allowed` 只说明功能权限检查；两者均不是具体业务操作的最终授权。
- `row_access` 固定为 `not_evaluated`。记录范围显示声明来源，不推断某条记录可见性；自定义入口仍须接入范围、ACL、事务内授权和字段过滤。
- 文件 ACL、导入导出额外权限、表单只读列、创建者限制、审批状态、敏感原值二次验证、业务字段格式和并发版本仍由各业务入口执行。
- 尚未添加任意自定义 API 的权限契约推断或业务记录级授权模拟；源码未登记的资源/字段拒绝诊断。
