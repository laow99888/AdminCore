# 分页响应与查询边界

修复 `StandardPagination` 在请求 `page_size=100` 时实际返回至多100条、响应元数据却始终写10的问题。现在从实际分页器读取生效容量，最后一页及空列表仍报告分页容量，不把当前结果条数当作每页大小。

| 项目 | 本批范围 |
|---|---|
| 入口 | 所有使用 StandardPagination 的列表；真实 HTTP 覆盖用户、角色及操作日志 |
| 默认与上限 | 默认10，上限100；超过上限截断，0、负数或非数字沿用现有回退10规则 |
| 依赖与兼容 | 使用现有 Django/DRF；无迁移、无新增依赖、响应结构不变 |
| 权限 | 保留各资源权限与数据范围；关闭的可选模块仍返回404 |
| 自动检查 | `cd backend; venv/Scripts/python.exe -m pytest tests/test_list_queries.py` |
| 真实服务 | `scripts/validate_minimal_build.py` 精简→完整→精简及桌面/窄屏登录 |

## 现有约定及剩余工作

全局分页默认10、最大100；人员选择器另有严格参数校验，非法输入返回400，保持原契约。列表过滤及排序由各 ViewSet 显式声明；安全导出通过登记资源和字段白名单限制，最多5,000行、10MiB，超过时拒绝。本地Excel导出仅含已加载的当前页。

用户批量操作最多1,000个UUID，重复、缺失和不可访问对象整批拒绝；保护关联导致删除失败时整个事务回滚。当前审计保存逐项结果，成功API仍沿用历史消息与空数据结构。文件回收站批量最多100项，各项检查权限、版本和冲突，明确返回逐项结果及成功/失败数。导入使用SQL逐行账本，逐行复核权限和原会话，接续时跳过已提交行。

P0第15项仍为部分完成：需要继续统一查询输入/排序与批量响应契约，补齐SQL执行/锁等待预算和混合权限并发、大数据验收。应用服务器超时不等于数据库语句已取消；现有列表查询次数检查也不能代替容量结论。
