## 已确认问题与后续验收标准

### B1 · P1：禁用后重新启用，旧登录凭据恢复可用

**证据类型：隔离数据库中，实际用户管理 API 和真实 JWT 会话复现。**

复现步骤：普通用户先登录；管理员通过单个 PATCH 或批量操作禁用该用户；旧 access 访问 `/api/v1/auth/me/` 返回 401；管理员再启用用户；同一个旧 access 又返回 200。第三个探针确认，启用后旧 refresh 也能刷新成功。

触发条件是旧凭据和设备会话仍在有效期内，且没有另外改密或撤销；**不是禁用期间仍可登录**。当前 access 有效期为 5 分钟、refresh 为 1 天，实际还受设备会话到期和闲置策略限制。账号因凭据泄露而禁用后，如果管理员仅重新启用账号，攻击者保留的旧凭据可能再次可用，因此应优先修复。

定位：`backend/apps/users/serializers.py:124`、`backend/apps/users/views.py:213`、`:216`。单个和批量启停只修改 `is_active`、资料版本，没有递增凭据版本或永久撤销旧会话。`backend/apps/auth_app/sessions.py:64` 检查当前状态，重新启用后条件重新满足。`User.save()` 也没有补上统一的禁用安全边界。

代码追踪还发现，开放 API 凭证同样依赖用户当前激活状态、密码摘要和 `session_version`，可能受同一根因影响；该可选模块未在公网启用，本轮没有运行其禁用再启用探针，不将其表述为公网已复现结果。

后续修复与验收：

- 将账号禁用定义为永久撤销此前凭据；统一处理单个、批量及 Django admin 写入口，保证原有事务、审计、版本冲突和锁顺序。
- 重新启用后，旧 access、旧 refresh、旧设备始终失效，新登录正常；补充独立 API 凭证相同生命周期检查。
- 保留“禁用期间立即拒绝”的已有行为，验证回滚、重复禁用和并发启停不会恢复已撤销凭据。

证据：`test_review_regressions.py`、`confirmed-regressions.log` 中前三个失败断言。

### B2 · P2：仪表盘按 UTC 分日，与系统上海日期错位

**证据类型：冻结时间的数据库探针。** 系统 `TIME_ZONE='Asia/Shanghai'`，而 `timezone.now().replace(hour=0,...)` 生成 UTC 零点；趋势直接使用 SQL `date(created_at)`，也未明确使用业务时区。

定位：`backend/apps/core/views.py:77`、`:83`、`:116`、`:117`。

### B3 · P2：用户导入校验不完整，超长字段中断后续行

**证据类型：独立 PostgreSQL 18.6 实际 API、任务及数据库结果。**

`create_user_row()` 只专门校验联系方式，随后直接调用 `create_user()`，没有正常用户创建接口所具有的用户名规则和字段长度校验。

复现结果：

- 用户名 `invalid user name2!` 被实际创建；正常创建接口采用的模型用户名规则不接受这种值。
- 导入三行：第一行合法、第二行 `first_name` 为 151 个字符、第三行合法。提交返回 200；任务随后抛出 `DataError`，状态为 failed，第一行已提交，第三行没有执行，只有一条行回执。
- 这是“部分写入后任务中断”，不是整批回滚，也不是数据被删除。接续账本仍存在，但同一非法行会再次阻塞，不能把人工接续当作字段校验修复。

定位：`backend/apps/data_io/resources.py:20`；`backend/apps/data_io/tasks.py:146` 仅检查通用单元格上限 32767，`:156` 的逐行错误处理未包括该 `DataError`，最终进入整个任务失败分支。

后续验收：让导入与正常创建共享无密码场景可用的字段校验，保留导入账号不可直接登录、无额外角色的约定；用户名格式、用户名/邮箱/姓名长度边界均有逐行错误；非法行写失败回执后继续处理合法行，结果计数准确，错误不保存原始联系方式。以真实 PostgreSQL 验证重复投递、接续不重复创建、审计与账本原子性。

证据：`probe_postgres_import.py`、`postgres-import.log`；诊断脚本捕获并记录异常后退出 0，只代表探针执行完毕，不代表导入行为正确。

### B4 · P2：备份文件权限依赖启动进程的 umask

**证据类型：隔离 Linux 中运行当前备份代码，快照命令由合成输出替代。** `umask 022` 时，新建备份目录为 **755**，数据库 dump、媒体压缩包、清单及完成标记为 **644**。没有显式收紧权限。

后续验收：POSIX 新建目录/文件最小权限为 700/600，覆盖 partial、成功、失败、回执和已有目标目录；对不安全的既有路径采取明确策略，不自动扩大或扰动未知权限。Windows 明确 ACL 支持边界；权限策略与独立副本/恢复脚本保持一致。

后续验收：设计持久删除意图、失败状态和可重试执行，使数据库与存储的不可逆操作有明确恢复路径；不能只把操作移到没有持久保障的 `on_commit` 就宣布可靠。覆盖审计/行删除/提交失败、进程中断、重复投递、本地及 S3；不得将缺失对象静默当作完整文件，也不得误删新引用对象。

### D3 · P1：发送通知期间持有操作者、收件人或管理员行锁

**证据类型：PostgreSQL 18.6 双连接实际复现。** `backend/apps/core/tasks.py:34` 外层事务内调用模板/任务失败通知服务；服务锁用户后在相同事务执行外部渠道。合成渠道内用第二连接更新发送人/收件人、以及两名管理员的行，四次触发 150ms 锁等待超时 `55P03`，事务结束后两次更新成功。

慢 SMTP/Webhook 因而会延长用户行锁持有时间，扩大普通写入等待。专项没有发送真实消息，也未声称线上已经发生事故；`task.failed` 的五次重试上限已实测存在，“无限重试”不成立。

后续验收：短事务领取任务/冻结授权与负载，外部 I/O 不占用户行锁，再用带版本或租约的状态写回；保留至少一次、幂等、撤权、失败补偿和未知送达结果语义。验证双连接用户写入不被慢渠道阻塞、并发领取、崩溃恢复、超时后迟到响应、重试上限，不能靠删安全锁或丢失可靠性解决。

### D4 · P2：文件上传未遵循统一业务响应信封

**证据类型：实际上传 API。** `backend/apps/files/views.py:177` 返回 201 裸 FileSerializer，缺少统一的 code/message/data；前端目前特殊处理，因此不能说所有上传都不可用。该文件的 OpenAPI 明确描述裸响应，不是“实现与 OpenAPI 同时不符”。

后续验收：确定并统一业务响应契约，同步前端、生成类型和文档；兼容现有调用者或给出明确迁移方式；覆盖上传成功、校验失败、权限失败、网络错误及文件预览/导入调用，不改变原生文件下载流协议。

### D5 · P2：数据库密码有弱默认值，生产未要求显式配置

`docker-compose.yml:21` 的 `DB_PASSWORD` 回退为 postgres，基础 settings 也有同类默认；production 只对应用密钥作强校验。缺失数据库密码的复制部署可能继续使用已知值。**没有读取部署密钥，未确认当前线上密码弱，数据库也没有因此被证明公开。**

后续验收：生产必须显式提供非空且符合策略的数据库凭据；开发便利配置单独声明，生成器继续生成随机值。覆盖空值、缺失、精简/标准构建和现有库升级；更换配置不等于实际修改已有数据库密码，不自动轮换用户现有凭据。

### D6 · P2：默认 HTTP 端口映射所有接口，缺少绑定地址配置

Compose 默认前端端口为 `${FRONTEND_PORT:-80}:80`，未提供绑定地址变量；配合默认关闭应用内 TLS，复制部署可能意外暴露 HTTP 入口。外部 TLS 代理是支持的模式，**当前 Tunnel 入口已有回环绑定与 TLS，不将它记为现有公网未加密。**

后续验收：增加显式绑定地址与安全默认配置，区分外部 Tunnel/TLS 和直接公开部署；验证 Compose 渲染、实际监听、可信代理、重定向与安全 Cookie，文档明确可访问边界。HSTS 域名范围按实际部署选择，不机械为所有子域强加长周期策略。

### D7 · P2：通知收件人列表缺少请求级数量上限

`NotificationCreateSerializer.recipient_ids` 使用 many=True 的主键字段，没有长度上限。实际接受 1,001 个条目；探针使用同一合成收件人重复值，并不等于已实际发送给 1,001 人。入口仅管理员可用，但仍会逐项查询/处理大请求。

后续验收：在逐个查库和持锁前限制条目数与总负载，定义重复、禁用收件人及空列表策略；同步核对消息和链接字段边界。测试 0/上限/上限+1、重复值、越权与异常对象，并验证拒绝时没有部分写入或大量无效查询。

### D8 · P2：实时事件地址写死，与 REST 自定义前缀不一致

REST 客户端支持 `VITE_API_BASE_URL`，`frontend/src/utils/realtime.ts:99` 则固定 `/api/v1/realtime/events/`。自定义同源 API 前缀时会出现 REST 与 SSE 路径不一致；源码已确认，当前标准路径没有故障，本轮未部署自定义网关。

后续验收：共享经过校验的同源 API 路径策略，明确代理重写与后端 ASGI 路径；支持的前缀可以重连/降级，不支持的跨源配置明确报错。**保留 SSE 只向当前源发送凭据的限制**，不能直接把 Bearer token 发往任意配置域名。

### D9 · P2：登录表单和图表缺少部分无障碍语义

`LoginView.vue` 的用户名、密码缺少明确 label/aria-label 和 autocomplete，主要依赖 placeholder；`BaseChart.vue` 没有等价数据摘要或表格。不是全站完全没有 focus-visible 或键盘支持。

后续验收：按现有组件系统补名称、用途与错误关联，允许密码管理器正确识别；图表提供有意义的文本/表格替代，键盘能访问关键内容。核对中文/英文、缩放、对比度和焦点；默认关闭的图片验证码另注明无障碍边界，不虚称已取得全面标准认证。

### D10 · P2：菜单树存在逐节点查询

`MenuSerializer.get_children()` 递归调用 `obj.children.all()`。实际菜单 API 中，4 个菜单节点为 7 次 SQL，24 个节点为 27 次 SQL，查询随节点增长；角色权限序列化另有绕过已预取结果的查询，也需同批核对。

后续验收：在保持授权过滤、排序、层级和异常环保护的前提下批量构造；对固定查询预算做 4/24/较大树回归，角色列表另测。当前结果来自隔离 SQLite，不能当成生产响应时间结论。

### D11 · P2：用户导入的逐行数据库工作量偏大

实际导入任务，2 行为 59 次总 SQL、45 次数据读写；12 行为 279/205，增加 10 行多出 220 次总 SQL、160 次数据读写。总 SQL 包含事务控制与 savepoint；没有据此证明特定吞吐、5,000 行必然超时或生产容量不足。

后续验收：分解权限重查、进度、审计与账本成本，减少冗余而保持逐行原子、撤权及时生效、接续和幂等；不把授权只校验一次作为优化。与 B3 一起用真实 PostgreSQL 测试小/中批量查询预算、耗时和任务中途撤权，明确部分成功与恢复语义。

### D12 · P3：中文批量操作成功提示返回英文

`backend/apps/users/views.py:235` 返回 `{action} success`；中文 API 请求实际得到 `deactivate success`，现有消息映射不覆盖这种动态文本。

后续验收：服务端成功消息使用明确可翻译消息或稳定业务码，中文/英文的启用、停用及其他批量结果正确；前端不要用整段动态英文作业务判断，与 A4 的词条检测共同覆盖。

### D13 · P3：响应信封包装未保留原响应自定义头

`backend/apps/core/mixins.py:38` 重新构造 Response 时只传数据和状态码。真实 helper 探针中，201 原响应的 Location 丢失；ETag/RetryAfter 等同类头也需验收。后续中间件增加的安全头不等于在这里全部丢失，未宣称所有当前接口均受影响。

后续验收：保留应继承的头及明确处理 Cookie，重新计算与响应体相关的 Content-Type/Content-Length；测试创建定位、限流重试、条件请求与流式响应排除，避免把文件响应错误包成 JSON。
