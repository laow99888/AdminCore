## 已确认问题与后续验收标准

### B1 · P1：禁用后重新启用，旧登录凭据恢复可用

**证据类型：隔离数据库中，实际用户管理 API 和真实 JWT 会话复现。**

复现步骤：普通用户先登录；管理员通过单个 PATCH 或批量操作禁用该用户；旧 access 访问 `/api/v1/auth/me/` 返回 401；管理员再启用用户；同一个旧 access 又返回 200。第三个探针确认，启用后旧 refresh 也能刷新成功。

触发条件是旧凭据和设备会话仍在有效期内，且没有另外改密或撤销；**不是禁用期间仍可登录**。当前 access 有效期为 5 分钟、refresh 为 1 天，实际还受设备会话到期和闲置策略限制。账号因凭据泄露而禁用后，如果管理员仅重新启用账号，攻击者保留的旧凭据可能再次可用，因此应优先修复。

定位：`backend/apps/users/serializers.py:124`、`backend/apps/users/views.py:213`、`:216`。单个和批量启停只修改 `is_active`、资料版本，没有递增凭据版本或永久撤销旧会话。`backend/apps/auth_app/sessions.py:64` 检查当前状态，重新启用后条件重新满足。`User.save()` 也没有补上统一的禁用安全边界。

代码追踪还发现，开放 API 凭证同样依赖用户当前激活状态、密码摘要和 `session_version`，可能受同一根因影响；该可选模块未在公网启用，本轮没有运行其禁用再启用探针，不将其表述为公网已复现结果。

后续修复与验收：

- 将账号禁用定义为永久撤销此前凭据；统一处理单个、批量及 Django admin 写入口，保证原有事务、审计、版本冲突和锁顺序。
- 重新启用后，旧 access、旧 refresh、旧设备始终失效，新登录正常；补充独立 API 凭证相同生命周期检查。
- 保留“禁用期间立即拒绝”的已有行为，验证回滚、重复禁用和并发启停不会恢复已撤销凭据。

证据：`test_review_regressions.py`、`confirmed-regressions.log` 中前三个失败断言。

### A1 · P2：客户端 IP 被记录成反向代理容器地址

**证据类型：上轮公网浏览器与本轮代码追踪。** 会话及审计记录保存 `10.203.87.5`，不能据此识别实际访问者。定位：`backend/apps/auth_app/sessions.py:30`、`backend/apps/auth_app/views.py:79`、`backend/apps/logs/audit.py:87`；Nginx 已在代理侧处理可信来源，并传递规范化转发头，后端上述逻辑仍取 `REMOTE_ADDR`。

后续验收：实现统一且可配置的可信直接代理解析；会话、登录和业务审计结果一致；可信/非可信来源、伪造转发头、IPv4/IPv6、多级链路、格式异常均有测试；验证上述可选模块的按访客限流不会误用容器地址。不直接无条件信任 `X-Forwarded-For`。

### B2 · P2：仪表盘按 UTC 分日，与系统上海日期错位

**证据类型：冻结时间的数据库探针。** 系统 `TIME_ZONE='Asia/Shanghai'`，而 `timezone.now().replace(hour=0,...)` 生成 UTC 零点；趋势直接使用 SQL `date(created_at)`，也未明确使用业务时区。

在上海 **10 月 16 日 10:00** 查询，将一条成功登录设为上海当天 **01:00**，实际“今日登录”为 0，趋势当天也为 0，记录被划入前一天。相同今日边界还用于操作数。

定位：`backend/apps/core/views.py:77`、`:83`、`:116`、`:117`。

后续验收：使用明确的业务时区计算日界线和日期聚合，避免数据库隐式时区；SQLite 和 PostgreSQL 均验证上海午夜前后、月末/年末、七日窗口起点及没有事件的补零，确认计数与前端日期标签一致。

证据：`confirmed-regressions.log` 最后两个失败断言。本轮没有用 PostgreSQL 重跑这两个日期探针，因此跨数据库一致性仍是修复验收要求。

### B3 · P2：用户导入校验不完整，超长字段中断后续行

**证据类型：独立 PostgreSQL 18.6 实际 API、任务及数据库结果。**

`create_user_row()` 只专门校验联系方式，随后直接调用 `create_user()`，没有正常用户创建接口所具有的用户名规则和字段长度校验。

复现结果：

- 用户名 `invalid user name2!` 被实际创建；正常创建接口采用的模型用户名规则不接受这种值。
- 导入三行：第一行合法、第二行 `first_name` 为 151 个字符、第三行合法。提交返回 200；任务随后抛出 `DataError`，状态为 failed，第一行已提交，第三行没有执行，只有一条行回执。
- 这是“部分写入后任务中断”，不是整批回滚，也不是数据被删除。接续账本仍存在，但同一非法行会再次阻塞，不能把人工接续当作字段校验修复。

定位：`backend/apps/data_io/resources.py:20`；`backend/apps/data_io/tasks.py:146` 仅检查通用单元格上限 32767，`:156` 的逐行错误处理未包括该 `DataError`，最终进入整个任务失败分支。

后续验收：让导入与正常创建共享无密码场景可用的字段校验，保留导入账号不可直接登录、无额外角色的约定；用户名格式、用户名/邮箱/姓名长度边界均有逐行错误；非法行写失败回执后继续处理合法行，结果计数准确，错误不保存原始联系方式。以真实 PostgreSQL 验证重复投递、接续不重复创建、审计与账本原子性。

证据：`probe_postgres_import.py`、`postgres-import.log`；诊断脚本捕获并记录异常后退出 0，只代表探针执行完毕，不代表导入行为正确。

### B4 · P2：备份文件权限依赖启动进程的 umask

**证据类型：隔离 Linux 中运行当前备份代码，快照命令由合成输出替代。** `umask 022` 时，新建备份目录为 **755**，数据库 dump、媒体压缩包、清单及完成标记为 **644**。没有显式收紧权限。

定位：`scripts/backup_runner.py:41`、`:149`、`:192`、`:196`、`:227`。临时文件创建阶段也需要保护，不能只在最终文件发布后补权限；回执与诊断文件同样应纳入检查。

风险条件是备份路径的父目录允许其他本机用户穿越；这会使业务库和私有媒体副本被非预期读取。**现有测试服务器 `/opt/admincore` 的 700 父目录已经阻断这条访问路径，本轮没有证明公网泄露或现有备份已被他人读取。** 可复用脚手架不能完全依赖部署者碰巧设置了安全 umask 或父目录。

后续验收：POSIX 新建目录/文件最小权限为 700/600，覆盖 partial、成功、失败、回执和已有目标目录；对不安全的既有路径采取明确策略，不自动扩大或扰动未知权限。Windows 明确 ACL 支持边界；权限策略与独立副本/恢复脚本保持一致。

证据：`probe_backup_permissions.py`、`backup-permissions.log`。未备份真实数据，也未证明真实恢复成功。
