# 流程版本、退回与超时运营深化第五批

承接[功能深化路线图](功能深化评估与路线图-2026-10-18.md)第 6 项和[第四批组织任职](组织任职与主管审批深化第四批-2026-10-18.md)，实现同编码流程版本发布、退回指定环节、超时提醒及通知升级、超时接收人异常重试。此批完成不代表整个深化路线图完成。

## 同编码多版本

`revision` 是新增的发布版次，旧记录从 1 开始。原 `version` 继续作为草稿编辑的乐观锁计数，原申请的 `flow_version` 也保留原含义，不把存量编辑版本重新解释成版次。申请增加只读 `flow_revision`。

发布版和归档版可以复制为同编码的新草稿；每个编码最多一份草稿、一份当前发布版。新草稿不影响正在接收申请的旧发布版。发布新草稿时原发布版在同一事务归档，后续申请和生成业务的 `flow_code` 查询使用新发布版；在途申请始终引用原流程行和原定义。归档停止接新申请，已有申请继续运行。恢复旧配置应复制旧版再发布新版本，不能直接改写已发布定义。

新建版本、发布、归档共用编码根行锁，数据库同时约束编码和版次唯一、单草稿、单发布版。流程编码仍沿用原有全局命名空间，未改成每租户可重复编码。**编码创建后不可更改**，包括草稿；需要改编码时应新建流程。旧客户端若依赖修改草稿编码，需要调整。原发布接口兼容省略编辑版本，新界面始终提交版本。流程生命周期写入显式审计投影。

设计器分别显示发布版次、编辑版本，提供新建版本和归档入口。分页列表支持 `code`、`status` 筛选及 `revision` 排序。每个旧版本都能查看；本批没有增加跨版本图形差异比较。

## 退回与历史

只有当前待办的审批人或受托人可以退回；管理员、申请人身份本身不能强制退回。目标必须是本次申请实际走过且完整通过的前序审批节点，不能是当前节点、开始、结束、未经过的分支或未完成的会签节点。必须填写原因和当前 `expected_workflow_version`，最多退回 100 次；已结束的申请不能退回。

退回取消当前未处理待办，保留已完成的历史步骤，新进入目标节点并增加步骤轮次 `sequence`。同一节点、同一审批人可在新轮次再次出现；或签、会签、转办、加签的同节点判断限定当前轮次，不与旧步骤冲突。原步骤决策、处理人和意见不被覆盖，操作历史分页显示退回来源、目标、原因、操作者和时间。

重新进入节点时按当前有效组织、角色和人员解析，并保存新的解析记录；原轮次仍保留原快照。若目标人员无效，退回事务整体回滚，原待办继续有效。后续环节按原流程定义和原申请输入重新执行，不支持退回后改写原始输入或跳过中间审批。关联生成业务仍为 `pending`、保持原业务版本和编辑锁，最终决策才事务回写。

新界面每次决策提交流程版本及待办步骤 ID，防止旧页面误处理重新生成的待办。为兼容旧客户端，未发生退回的旧接口仍可省略流程版本；**发生过退回后，决策和加签/转办/委托必须携带当前流程版本**，缺失返回 400，过期返回 409。修复审批人仍以明确步骤 ID 和步骤版本保护。

实际 PostgreSQL 并发测试发现用户 `FOR UPDATE` 锁与新步骤外键的 `KEY SHARE` 锁形成死锁。本批将公共写授权的用户锁在支持的平台改为 `FOR NO KEY UPDATE`，仍串行化用户授权写入、阻塞撤权所需更新锁，同时允许外键引用。其他平台保留原锁方式。不同审批人同时退回、两任务重叠扫描，以及外键可引用而撤权锁不可穿透均有 PostgreSQL 回归；未绕过写授权。

## 超时、通知升级和异常重试

只在 V2 审批节点显式配置，不配置即关闭。例如：

```json
{"timeout":{"minutes":60,"escalate_after_minutes":120,"escalate_to":"有效人员UUID"}}
```

提醒时限为 1～525600 分钟。升级时限和接收人必须一起设置，升级必须晚于提醒且不超过同一上限。界面中的 0 表示移除相应配置。发布时校验升级人员可选范围；进入步骤时冻结截止时间和升级人员，后续变更流程不修改已有待办。加签继承当前节点截止时间；转办、委托不重置时钟，也不会重发已受理的同一步骤提醒。再次进入节点会获得新的步骤和时限。

`approvals.scan_overdue` 每次默认扫描 100 个步骤，接口上限 1000；重叠任务在申请锁下复核待办、步骤、时间和处理标志。提醒发给当前受托人或审批人，升级发给配置的接收人，每步骤每种通知最多入队一次。通知仅包含通用标题、申请和步骤标识，不复制业务金额或快照。**升级指站内通知升级，不自动转办、通过、拒绝或增加数据访问权**；接收人没有原申请权限时不会因升级获得详情权限。

使用现有 Outbox；系统动作不冒用申请人身份，`actor` 为空、元数据带系统标记。`queued` 只表示可靠通知队列已受理，不表示送达。`reminded_at`、`escalated_at` 是扫描处理时间，接收人无效也会记录处理结果，并以 `timeout_error` 区分，不能把非空时间当成发送成功。实际送达情况仍在通知中心确认。站外供应商凭据和可选集成保持关闭。

无效、停用或租户成员失效的接收人不发通知，记录 `unavailable` 和异常标志，避免每分钟重复轰炸。管理员可在异常审批详情中恢复账号或修复审批人后，填写原因、提交步骤 ID 和当前步骤版本重试；升级接收人失效时可选择替代接收人。只重新开放失败种类，不清除已入队成功的标志；扫描后再次尝试。操作本身写入审批历史和审计。

管理员“异常审批”增加超期待办，保留原审批人缺失/停用修复入口。此处覆盖失效审批人和超时通知接收人的处置；未实现所有配置阻塞的主动诊断、任意管理员强制跳转、真正并行分支汇聚或自动换算工作日 SLA。下一节点解析失败仍回滚当前决策并返回可修复错误。

## 升级与接口

新迁移 `approvals.0007_remove_approvalstep_unique_approval_step_assignee_and_more`，保留旧申请、原流程外键、编辑版本、当前步骤、人员和解析快照；旧待办不补算超时时间。旧步骤唯一约束扩展到轮次。迁移测试从 0006 实际创建旧流程和待办，再升级验证。

- POST `approvals/flows/{id}/new-revision/`：复制发布或归档版。使用 JSON 请求体 `{}`，支持幂等键。
- 原流程发布/归档接口继续使用；列表新增编码筛选和版次排序。
- POST `approvals/{id}/return-node/`：`target_node`、`comment`、`expected_workflow_version`，支持幂等键。
- GET `approvals/{id}/history/`：按原申请可见范围查询操作记录，分页返回。
- POST `approvals/{id}/retry-timeout/`：管理员提交 `step_id`、`expected_version`、原因及可选替代升级人员，支持幂等键。

部署后运行现有 `python manage.py configure_maintenance`，新增每分钟扫描计划；幂等录入保留管理员已有启停和时间修改。审批模块关闭时不录入也不执行扫描。该命令只登记计划，实际调度仍需原有 beat/worker 和 Outbox 派发。本轮只在隔离验收库执行，未改用户现有数据库或服务器。

同时修复旧审批写响应未传字段权限上下文的问题：通过、拒绝、转办等返回的业务快照也按当前操作人的字段权限脱敏。生成采购的专项实际验证限制金额读取后，审批写响应不返回原金额。
