# 不可变镜像发布与复核

开发时保留原来的 Compose 构建方式。发布前使用 `scripts/prepare_release.py` 构建一次 backend 和 frontend，将所有启用的服务固定到本机内容镜像 ID；worker、beat、realtime 必须与 backend 的构建定义一致，否则拒绝准备。数据库、Redis 等第三方镜像也记录本机已拉取的内容 ID，缺失时先显式 `docker compose pull --ignore-buildable`。工具只准备文件，不启动、停写、迁移或替换服务。

在待发布源码和已经核对的 `.env` 所在目录执行，发布前另行完成备份与迁移审查：

```powershell
python scripts/prepare_release.py --output .codex-validation/releases/本次发布
docker compose -f docker-compose.yml -f .codex-validation/releases/本次发布/compose.release.yml up -d --no-build --wait
python scripts/prepare_release.py --output .codex-validation/releases/本次发布 --verify
```

如使用 `compose.minimal.yml`、`compose.build-minimal.yml`、`compose.realtime.yml`、项目归属或 Tunnel 覆盖文件，准备、启动和复核三步必须以同一顺序显式传递全部文件，发布覆盖文件最后叠加；项目名、环境文件和 profiles 也必须保持一致。工具的 `-f/--file` 可重复，支持 `--root`、`--env-file`、`-p/--project-name`。启用服务集合不同、Python 构建参数不同或旧发布目录已存在都会拒绝。

输出只有 `compose.release.yml` 和 `manifest.json`：包含服务名、内容 ID、项目名和 UTC 时间，不包含 `docker compose config` 解析出的环境值或容器 inspect 内容。覆盖文件清除所有构建定义并设置 `pull_policy: never`；部署再使用 `--no-build`。后续改动 `latest` 等标签不会改变本次发布所指的内容。

`--verify` 核对覆盖文件/清单一致、有效服务集合、禁止构建/拉取，以及每个实例实际使用的镜像 ID、运行和已有健康检查结果。它不能替代登录、业务、备份恢复或容量验收，也不证明源码已审查、构建可复现或第三方镜像无漏洞；发布记录仍应关联 Git 提交、源码归档和校验清单。备份 runner 等需要检查的 Compose 包装器应固定本次文件列表，并按原运维流程验收。

内容 ID 属于当前 Docker 引擎。跨服务器使用时应将清单内镜像显式 `docker image save` 后传输、校验并 `docker image load`，或建立登记仓库的 `image@sha256:digest` 发布流程；不能只复制覆盖文件后期待自动拉取。保留上一发布镜像/清单，数据库回退另行设计；工具不执行数据恢复。

`python scripts/validate_release.py` 使用五个无网络、无端口、无业务数据的合成容器，验证四个 Python 角色同 ID、环境不导出、构建标签改指后固定 ID 启动、停止恢复及运行状态复核。应用角色的真实探针、迁移和备份恢复继续由项目模板及相应专项验收覆盖。
