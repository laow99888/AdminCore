## 关联与日志契约

HTTP 使用服务端生成的请求 ID；只接受最长100字节、ASCII字母数字及 `-_.` 的上游 X-Request-ID。该值用于定位，不能作为可信身份或授权凭证。请求结束输出状态和响应生成耗时；流式响应的耗时不包含之后传输/消费时间。

Outbox 保存请求 ID；没有 request 对象时继承当前安全上下文。批量派发逐事件切换关联上下文，退出后恢复；登记维护/导入发布 Celery `headers.request_id`，任务信号设置/恢复 request_id 和 task_id。模板通知投递保存原请求 ID，事件处理日志包含安全的 event_id、record_id或delivery_id；业务审计仍按原事务与权限保存。任务结果详情新增请求关联 ID。定时任务/旧任务没有 HTTP 来源时为空，不伪造关联，不回填旧数据。

Django控制台及显式单进程文件日志采用白名单 JSON：UTC时间、级别、logger、事件、关联 ID、状态码、耗时、异常类型、源文件基名/行号及最多12个代码栈位置。Celery worker复用同一配置，不恢复默认带任务参数/结果/异常原文的日志格式。固定登记消息可保留未插值的 message_template；未知第三方日志仅保留级别及来源。任何 msg 参数、请求头/路径/查询、Cookie、正文、任意extra、异常消息、完整路径和源码行都不序列化。由此会减少第三方错误原文的诊断细节，定位依靠类型/代码位置及受控审计，不声称覆盖 Nginx/Docker/数据库或外部服务全部日志。部署层仍需控制其日志权限与轮转。

诊断页关联数量只是有请求 ID 的记录数，不证明所有历史记录都有来源，也不构成分布式追踪/APM。跨外部系统传播、外部告警平台和新增业务任务必须另行接入验收。

## 指标口径

- broker ready读取固定默认celery队列及Kombu优先级桶的LLEN之和；不含已领取/未确认/延迟任务，不证明worker或beat存活。当前项目只使用这组默认队列，未来自定义路由必须扩展登记。
- TaskRecord按持久状态计数；最早1000条pending/running记录按自身保存的queue_expiry、hard_timeout+60秒判断候选。没有有效策略/起始时间归未分类，超1000条明确截断；不改状态、不自动重试或删除。
- 耗时采用最近1000条已结束且有起止时间的任务，负时差排除；返回样本数、平均、最近秩p95、最大值。无样本为null，不能据此推断全历史或长期性能。
- 可靠事件/模板投递按状态计数及最老pending/failed年龄；terminated/succeeded不算积压。缺失/失败指标显示未采集，不用0冒充健康。SQL有界超时但统计总量仍可能扫描，超大项目需独立时序聚合后再验收。

## 存活与就绪

`GET/HEAD /api/v1/health/live/` 只说明HTTP进程能响应，不访问数据库/Redis。既有 `/api/v1/health/` 保留为数据库与所需缓存的就绪检查；失败503，仅返回status，无连接详情。两者均禁止缓存，POST405。就绪不等于worker、调度器、SMTP、对象存储或生产TLS健康；这些仍须独立监控与真实依赖验收。
