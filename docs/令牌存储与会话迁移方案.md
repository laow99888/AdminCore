# 令牌存储与会话迁移方案

## 当前实现与威胁模型

前端通过 `src/auth/tokenStorage.ts` 统一读写 `token` 与 `refreshToken`。适配器目前仍使用既有 `localStorage` 键名，因此旧客户端、刷新轮换、多标签协调、SSO 和 SSE 行为保持兼容。令牌不进入 URL、日志、浏览器事件或微前端身份摘要；实时连接只向同源地址发送 Bearer 请求头，刷新轮换使用 Web Locks（无锁时有并发回退），退出会清除两类令牌。

`localStorage` 的主要风险是：同源脚本一旦已经执行，就可以读取令牌并代用户发起请求。本轮未发现可执行 XSS；这不等于 localStorage 可以抵抗 XSS，也不把 HttpOnly 描述为能阻止已执行脚本代用户请求。CSP、依赖审计、输出编码和危险 HTML 边界仍是独立控制项。

## 推荐迁移边界

后续如果部署条件允许，优先由同源 BFF 或后端会话端点完成迁移：

1. refresh/session 改为 `HttpOnly; Secure; SameSite=Lax` Cookie，服务端轮换并撤销会话；跨站登录回调只交换一次性短期 code，不把 token 放入 URL。
2. access token 只保存在内存，由请求适配器取得；刷新端点使用 Cookie，并检查 CSRF token、Origin/Referer 和明确的状态变更方法。
3. SSE 继续使用同源请求，通过 Cookie 或受控的同源 fetch 鉴权，禁止把 token 拼接到 URL；页面隐藏、退出和会话撤销时中止连接。
4. 通过 `BroadcastChannel` 或受控 storage 事件同步登录、刷新、退出和会话撤销；旧客户端保留兼容窗口，成功迁移后再清除旧键。
5. 设置闲置过期、绝对过期、刷新重放检测和单设备/全部设备撤销策略；迁移失败时只能回退到明确的旧客户端兼容路径，不静默恢复过期会话。

当前代码已经把业务读写收口到适配器，便于一次性替换上述边界；实际 Cookie/BFF 迁移需要服务器、反向代理、CSRF 策略和真实浏览器环境共同验收，不能只凭单元测试标记完成。

## 迁移验收矩阵

| 场景 | 必须验证的结果 |
| --- | --- |
| CSRF | 跨站 POST/PUT/PATCH/DELETE 被拒绝；同源合法请求通过；错误不泄露会话信息 |
| 刷新轮换 | 并发 401 只产生一次有效轮换；旧 refresh 重放失败；新 access 不被旧响应覆盖 |
| 多标签 | 登录、退出、撤销和过期在其他标签可观察；不会把新用户请求重放为旧用户 |
| 退出 | 服务端会话撤销，Cookie/内存凭据清除，SSE 与待处理请求停止 |
| SSO | 回调 code 一次性、短时有效；地址栏和历史记录不含 access/refresh |
| SSE | 只访问同源入口；不带 URL token；撤销或过期后有限重连并转入重新登录 |
| 闲置过期 | 闲置和绝对过期均按策略失效；过期响应不恢复旧页面敏感数据 |
| 历史客户端 | 兼容窗口内旧版本可完成迁移；窗口结束后旧 localStorage 令牌被拒绝并提示升级 |
| 部署 | HTTPS、代理 Cookie 属性、CORS、跨子域和 Tunnel 转发行为与本地一致 |

## 当前状态

R3 仍为**部分完成**：已完成统一存储边界、威胁模型、迁移设计，以及下述默认关闭的后端 Cookie 传输。当前网页仍使用旧适配器；前端内存存储、首次加载恢复、多标签协调、SSE 和真实浏览器/HTTPS 部署矩阵尚未完成，不能据此宣称站点已迁移。

## 后端 Cookie 传输契约（2026-10-17）

`AUTH_BROWSER_COOKIE_ENABLED=False` 为默认值。关闭时新端点及显式 Cookie 协商返回 404，旧 Bearer 客户端行为保持不变。非调试环境启用该能力必须配置 `USE_TLS=True`，并由可信代理正确转发 HTTPS；运行时仍拒绝非 HTTPS 或未启用 Secure Cookie 的请求。前端迁移与真实浏览器验收完成前，保持测试站点和正式环境的开关关闭。

| 请求 | 作用及边界 |
| --- | --- |
| `GET /api/v1/auth/browser-session/` | 匿名取得 `data.csrf_token` 并设置 CSRF Cookie；禁止缓存，不读取或返回 refresh/access |
| 登录、注册、双因素会话替换及 SSO complete，附 `X-AdminCore-Session: cookie` | 必须同源且通过 CSRF 后才执行签发；成功响应移除 refresh，保留 access、用户和原有恢复码等字段，增加 `session_transport: cookie` 与 `csrf_token`，refresh 仅写入 HttpOnly Cookie |
| `POST /api/v1/auth/browser-session/` | JSON `{}` 用于首次恢复；已有 access 的客户端传 `{ "session_id": "access 中的 sid" }`，防止旧标签轮换替换后的身份；只读取 Cookie，拒绝 body refresh，返回 access 并轮换 Cookie |
| `DELETE /api/v1/auth/browser-session/` | JSON 必须包含 `session_id`；无需有效 access，通过 Cookie 撤销当前设备并清除 Cookie，已失效或已退出仍返回 204；身份不符返回 409，保留替换后的会话 |

上述 Cookie 状态变更都要求 `X-CSRFToken` 和与请求 scheme/host 完全相同的 `Origin`；`CSRF_TRUSTED_ORIGINS` 不会放宽此同源约束。仅有 Cookie 不能访问 `me` 或其他业务端点；业务鉴权继续使用显式 Bearer。新端点保留全局匿名限流，并拒绝未知 JSON 字段及超过 4096 字节的请求。公开白名单只新增该精确路径。

HTTPS 使用 `__Host-admincore_refresh; HttpOnly; Secure; SameSite=Lax; Path=/`，不设置 Domain，避免子域通过父域 Cookie 干扰会话。HTTP 调试使用独立名称 `admincore_refresh_dev`，生产模式不会读取该调试 Cookie。Cookie 的有效期受 refresh 与设备绝对期限约束，轮换沿用已有用户行→会话行锁、单次 jti、闲置/绝对过期、改密/版本/禁用/SSO 撤销检查，不另建第二套会话账本。数据库及审计仍不存储可直接使用的 refresh 原文。

签发新身份时轮换 CSRF，刷新时保留 CSRF，避免同身份多标签互相失效。刷新失败不发送清除 Cookie 的响应，防止较晚返回的旧失败覆盖较早成功的轮换；session_id 不匹配也不改写 Cookie。客户端仍须将签发、刷新、恢复及退出纳入同一跨标签协调，失败后不得把旧请求作为新身份重放。此处的服务端保护不能替代尚未完成的前端并发协议。

OpenAPI/SDK 已描述协商头、必填 CSRF 头与新端点响应；Cookie 专用响应不发布 refresh 字段，兼容端点的 refresh 改为可选。当前网页调用仍使用原有 Bearer 模式，不会因 SDK 更新自动启用 Cookie。
