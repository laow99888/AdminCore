# 模块与基础能力（契约 v1）

本文说明现行模块契约。模块和默认值的真源为 [注册表](../backend/apps/core/modules.py) 与各 manifest；扩展入口、测试和专项手册见 [能力地图](ai/能力地图.md)。生成器 v2、在线表单、报表及物理精简构建均已实现；日期报告用于追溯对应批次。

## 预设与部署

核心认证、用户、权限、菜单、审计、仪表盘始终保留。可选模块如下：

| 模块 | 入口 | 模块依赖 |
|---|---|---|
| files | `/files`、`/api/v1/files/` | 无 |
| tasks | `/tasks`、`/api/v1/tasks/` | 后台执行使用 Redis、worker；调度使用 beat |
| notifications | `/notifications`、`/api/v1/notifications/` | 无业务模块依赖 |
| data_io | 用户导入导出按钮、`/api/v1/data-io/` | files、tasks |
| approvals | `/approvals`、`/api/v1/approvals/` | notifications |
| system | `/system/config`、`/system/dictionaries` | 无业务模块依赖 |
| organization | `/organization`、`/api/v1/organization/` | 无业务模块依赖；已配置的数据范围始终执行 |
| realtime（默认关闭） | `/api/v1/realtime/events/` | 需独立 ASGI 服务；参见实时通道文档 |
| example（默认关闭） | `/example`、`/api/v1/example/items/` | 无队列依赖；system 可选用于管理参数 |
| api_credentials、sso（默认关闭） | 机器凭证、OIDC 身份 | 以各 manifest 依赖及供应商配置为准 |
| feature_flags、ip_policy（默认关闭） | 灰度、IP 策略 | 按需启用并验证当前策略 |
| online_forms、reports（默认关闭） | 在线表单、报表看板 | 按各 manifest 配置依赖；跨能力接入另需审批/文件等模块 |

`.env` 未设置 `ADMINCORE_PRESET` 时沿用 `standard`。`minimal` 关闭全部可选模块，`standard` 启用 manifest 中 default_enabled=True 的模块，`demo` 仅用于非生产环境并创建固定凭据演示账号。生产拒绝 `demo` 和 `bootstrap_admincore --demo`。

`ADMINCORE_MODULES` 未设置时采用预设；显式空字符串关闭全部可选模块；逗号列表覆盖预设。未知名称、重复名称、缺少依赖立即报启动错误。参考根目录 `.env.modules.example`。

本地 Compose 更新代码时，同时构建 backend/worker/beat/frontend，启用 realtime 时连同其构建与重建。正式发布优先使用 [不可变镜像](不可变镜像发布与复核.md)，所有 Python 角色使用相同发布内容：

```powershell
docker compose build backend worker beat frontend
docker compose up -d
```

模块配置改变后，必须重新创建读取配置的 API、worker、beat 容器；只执行 `restart` 不会载入修改后的环境变量：

```powershell
docker compose up -d --force-recreate backend worker beat frontend
```

新精简部署（仍需准备 `.env` 中数据库和初始化管理员的强密码）：

```powershell
docker compose -f docker-compose.yml -f compose.minimal.yml up -d --build db backend frontend
```

**已有标准部署转精简**：先停止 `worker`、`beat`，再按精简命令重新创建 backend/frontend，确认就绪后停止原 `redis`。Compose 的 profiles 不会自动停止上一次运行的容器。重新转标准时，将 `.env` 预设设为 `standard`，检查显式模块列表，按标准命令启动完整服务。保持数据库、媒体卷，禁止使用 `down -v` 作为切换方式。

精简 Compose 使用一个 Gunicorn 进程、四个线程及本地缓存，实测仅 db/backend/frontend 三服务即可登录及运行核心页面。它不提供多进程或多副本共享的限流计数；扩大部署须选择共享缓存和相应服务。运行时关闭不会从 Python 环境、数据库或已构建前端产物中删除依赖。

增加 `-f compose.build-minimal.yml` 可选择物理精简构建：后端使用同版本/同哈希的精简锁文件，前端在构建时排除可选业务页面、PDF/富文本和本地 Excel Worker。完整 app/模型/迁移仍保留以支持原库升级。精简镜像不能通过环境变量补回缺失能力，启用可选模块前必须同步重建完整前后端；具体命令、切换及回退边界见[精简构建与完整恢复](精简构建与完整恢复-2026-10-15.md)。

## 关闭、升级和重新启用

后端依据声明注册 API；中间件也阻止已有 URL 缓存及可选 app 的 Django admin 入口。前端依据认证后的 `/api/v1/modules/` 契约阻止页面入口、过滤菜单、隐藏相关轮询和导入导出按钮。契约加载失败进入可重试页面。

所有 Django app 保留在 `INSTALLED_APPS`，关闭时仍执行迁移并保留表、数据、媒体及审计。调度器只读取已注册且启用的任务，已有 `PeriodicTask.enabled` 不被切换覆盖；业务消费者执行前再次检查模块。重新启用沿用原数据和计划。新增 app 必须显式加入安装列表和声明；后续的[模块扩展与示例工单](模块扩展与示例工单-2026-10-15.md)统一声明新模块权限/菜单/参数/范围/审计，前端在显式扩展登记中接入懒加载页面。它不自动安装任意第三方插件。

迁移 `core.0002`、`0003`、`0004` 为新增表/字段，不重写旧账户、密码、菜单配置或已有文件。旧代码回退应保留新表和数据；不要反向迁移删除新功能数据。升级前备份并验证已有库，回退代码和回退数据库分别评估。

## 系统参数与品牌

管理权限为 `config:read` / `config:update`。当前白名单只有产品名称、登录说明、Logo、软删除文件保留天数、已读通知保留天数。类型、默认值、范围由代码定义；系统参数接口不能写入密码、密钥、任意 Django 配置或权限边界。

启用 system 时，数据库覆盖值优先于环境变量/default；文件和通知保留期分别以 `FILE_SOFT_DELETE_RETENTION_DAYS`、`NOTIFICATION_RETENTION_DAYS` 为默认。关闭 system 后使用默认值，原数据库覆盖值保留。恢复默认应提交显示的默认值及当前版本。

新建覆盖值提交 `version=0`，更新提交读取到的版本；并发冲突返回 409。前端保留输入，单项保存不重置其他未提交项。记录审计前后值；每次读取先查询数据库版本，再取五分钟版本缓存，因此 API/worker 下一次读取就使用新版本，不依赖广播失效旧缓存。

公共 `/api/v1/brand/` 仅返回名称、说明、Logo，用于未登录页面和浏览器标题。失败回退默认品牌。Logo 支持 PNG/JPEG/WebP，原文件不超过 200 KB、尺寸不超过 1024×1024，服务器从解码像素重新生成最长边 256px 的 PNG，清除元数据；拒绝 SVG 和外部 URL。结果以内嵌 PNG 存入参数，不依赖公开媒体目录，审计仅保存摘要。Logo 是公开品牌资源，不应包含私密内容。

## 数据字典

管理权限为 `dictionary:read` / `dictionary:update`；业务选项接口仅要求认证。字典编码创建后不可改变，字典及字典项均可停用；不提供硬删除接口。每字典最多 500 项，值唯一，限制字段、长度及排序。任务/审批状态机枚举保留代码定义，不能通过业务字典修改合法状态迁移。

写入同样提交版本并返回冲突，审计包含前后值。选项按数据库版本缓存，只返回启用字典的启用项目；停用字典返回 404。前端业务页面可使用：

```ts
const { items, version, loading, error, reload } = useDict('customer_level')
```

首次挂载加载，修改字典后调用 `reload()`；未提供长期前端静态字典缓存。字典内容对所有已登录业务用户可读取，不用于私密字段或权限规则。

## 组织与数据范围

组织维护仅允许 `is_staff` / `is_superuser` 管理员，包括部门树、人员归属和角色范围。角色写操作、用户角色分配也仅允许管理员，避免通过停用、删除或修改角色授权逃逸范围。只有名为“系统管理员”的普通角色，不等同于管理员身份。

部门禁止循环，停用父部门前须处理启用的子部门；有关联的部门禁止删除，允许停用。主部门归属记录不能换绑用户；兼任部门、主管链及任职历史通过独立任职记录管理，见 [组织任职](组织任职与主管审批深化第四批-2026-10-18.md)。部门、人员归属、范围规则均有编辑版本和审计，PostgreSQL 使用一致的部门锁顺序保护并发。

支持注册资源的本人、本部门、部门及下级、自定义部门、全部范围；当前资源从模块契约读取，新增业务需显式登记。有效角色范围取并集，管理员绕过资源范围；未配置范围的资源沿用此前规则：用户/任务/日志为功能权限允许的范围，文件为本人归属。**配置了范围后**必须同时满足现有接口权限和资源范围；停用角色不退回未配置的宽范围。

用户列表、详情、修改、删除、重置密码、批量操作、导出；文件列表、下载和删除；任务查看、取消和历史清理；日志、统计均使用统一范围入口。批量用户请求包含越权、缺失或重复 ID 时整体拒绝，不执行部分修改。部门及自定义范围不包含未分配部门的人员。

受限用户范围不能创建/导入未分配部门的新用户，须由管理员创建并分配归属。导入任务保存发起人，读取源文件时检查归属范围，执行前及逐行再次校验账户状态、导入权限与用户范围；中途撤权停止后续行，已完成的行保留并记录结果。审批仍使用参与人规则，通知仍按收件人隔离。旧个人资料的自由文本 department 不自动迁移成组织关系。

关闭 organization 只撤下维护入口，仍执行持久化范围，避免扩大权限。不要通过关闭管理模块撤销安全策略。

## 权限与菜单刷新

后端每次请求查询当前角色权限；前端路由最多复用 30 秒的账户/模块契约。已打开、可见页面每 30 秒刷新账户、模块和菜单，重新聚焦或从后台返回立即刷新。权限被撤销时按钮更新，当前受限页面转 403；服务故障转可重试页面，不依赖重新登录。浏览器后台节流时不承诺定时器绝对时限，以返回前台触发补偿刷新；后端鉴权始终独立执行。

## 可重复验收

常规检查采用项目既有命令：后端 pytest、`manage.py check`、`makemigrations --check --dry-run`、严格 spectacular；前端 lint/build、Vitest 覆盖率、Playwright 和 bundle 预算。

独立 Docker/PostgreSQL 验收：

```powershell
backend\venv\Scripts\python.exe scripts\validate_foundation.py
```

需要空闲 18420/18421 端口。脚本生成独立 project 和随机临时凭据，只访问自己的测试库，验证新空库、精简三服务、启停数据保留、真实 HTTP 并发冲突、部门环路与配置错误。成功关闭自己的容器/删除测试卷和临时凭据，保留 JSON 报告；失败保留日志及隔离环境，按报告中的独立 project 清理，不得作用于在用 admincore 项目。Nginx 使用 Docker DNS 动态解析后端，兼容容器 IP 变化（[官方 upstream resolve 文档](https://nginx.org/en/docs/http/ngx_http_upstream_module.html)）。
