# 发布与版本策略

产品源码版本唯一来源是 [base-version.json](../backend/config/base-version.json)。本轮准备首个正式版本 **v1.0.0**，是否已经发布以 [GitHub Releases](https://github.com/laow99888/AdminCore/releases) 和对应 Git 标签为准；仅改 JSON 或通过历史 CI 都不等于新版本已发布。

## 各类版本的职责

| 标识 | 唯一来源 | 变更规则 |
|---|---|---|
| AdminCore 产品版本 | backend/config/base-version.json | 语义化版本，系统信息与 OpenAPI 同源；发布说明维护在 CHANGELOG |
| 模块契约版本 | 同一 JSON 的 module_contract_version | 只有契约变化才评估升级，不随产品补丁自动增加 |
| API 版本 | /api/v1 与 API 生命周期配置 | 按废弃窗口和替代接口迁移，不随依赖更新改路径 |
| 前端 npm 包版本 | frontend/package.json 及 package-lock.json | 构建包标识，不能用它推断底座已正式发布 |
| Python/Node/库/镜像 | [版本要求](../版本要求.md) 指向的配置与锁文件 | 固定版本、哈希/镜像内容 ID；更新后重新验证 |
| 下游业务版本与基线 | 业务自己的产品版本；admincore.project.json | 业务版本独立；底座版本/SHA 只在升级验收后推进 |

稳定版后的兼容修复用补丁版本，兼容新增用次版本；破坏性接口/模块契约变更用主版本并给迁移方案。开发候选可用 -rc.N。v1.0.0 不代表所有可选供应商都已启用，不构成 LTS 或不限规模的性能承诺。

## v1.0.0 的范围与边界

基座包括认证/权限/组织/租户/字段策略、通用页面与列表、私有文件、导入导出、审批、通知与任务、生成器 v2、版本化在线表单、报表、独立项目与三方升级工具。详细导航见 [能力地图](ai/能力地图.md)，变更及兼容边界见 [CHANGELOG](../CHANGELOG.md)。

外部邮件、短信/Webhook、企业 SSO、机器身份及异地 S3 按需启用；此前公网交付保持关闭。完整产品测试可用隔离供应商夹具，不等于每个真实供应商已验收。业务规则、容量目标、业务数据迁移和恢复目标由下游项目单独验收。

## 正式发布步骤与完成标准

1. 同步唯一版本、CHANGELOG、SDK 中的 OpenAPI 版本与本次兼容/迁移说明；执行文档契约和针对性回归。保留无关工作区修改，提交只含本次文件。
2. 推送发布候选提交，等待该 SHA 的完整项目 CI、依赖扫描和适用性能作业通过。失败先修复重新提交；不得借用旧 SHA 的通过结果冒充新版本验证。
3. 核对功能变更的真实基础设施/浏览器/迁移/备份验收；若仅版本与文档变化，明确沿用哪份已验收产品证据及差异。产品部署用不可变发布清单核对所有 Python 角色。
4. 在全绿候选 SHA 创建唯一 v1.0.0 标签及 GitHub Release，正文列范围、检查链接、迁移和回退边界。标签不移动，失败后以新的版本修复。源码包不包含运行凭据、媒体或业务数据。
5. 发布后核对标签/Release 指向候选 SHA。服务器是否部署是独立状态，不能将发布标签当作服务器已升级。

正式发布完成的证据是：版本一致、准确 SHA 的检查成功、标签与 Release 指向一致、说明可追溯。服务器发布按 [部署指南](部署指南.md) 和 [不可变镜像发布](不可变镜像发布与复核.md)，不能跳过备份或把删卷当回退。

## 下游采用

新项目使用已发布标签或审核 SHA 创建；已 fork 项目不覆盖业务代码，按 [底座升级](底座版本与项目升级.md) 审阅三方差异、迁移与业务回归。业务所有者自己的凭据、部署和数据保持独立。
