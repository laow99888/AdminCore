# 底座版本与项目升级

底座版本唯一来源为 `backend/config/base-version.json`，系统信息和 OpenAPI 共用该值。首个正式版 v1.0.0 已发布，准确提交及版本职责见 [发布策略](发布与版本策略.md)；不承诺未约定的维护期限。前端包版本、API `/v1/` 和模块契约分别管理，不能随依赖补丁升级随意改变。

## 创建独立项目

使用版本要求中的 Python、Git、Docker Compose。以下一条命令从当前已提交 HEAD 创建并启动精简项目，目标必须是底座目录以外的全新目录：

```powershell
python scripts/create_project.py D:/Projects/my-admin --name my-admin --preset minimal --frontend-port 8080 --backend-port 8001 --start
```

标准预设改为 `--preset standard`。`--ref` 可指定已审核的提交或标签；导出只读取该 Git 提交，不复制工作区未提交变更、Git 历史、实际环境文件、媒体、备份、依赖目录或构建产物。脚本从 `.env.example` 生成三个独立随机密钥，首次管理员密码只写入新项目 `.env`，登录后必须改密。Windows 文件权限继承目标目录 ACL，请选自己的私有工作目录。

默认精简为 PostgreSQL/backend/frontend；标准增加 Redis/worker/beat。全部仅本机访问，外部邮件、备份、图片处理默认关闭。首次构建需要网络和足够资源；实际端口占用仍可能在预检后改变。公网发布需另行配置 TLS、域名和可信代理。

生成项目包含 AI 开发入口：先读根目录 AGENTS.md，再按 docs/ai/README.md 定位。PROJECT.md 记录本实例启动方式；业务特有规则使用 docs/ai/业务上下文模板.md 建立上下文。创建器仅读取已提交快照，新入口必须先提交才会进入实际导出。

在生成项目中执行：

```powershell
python scripts/project.py status
python scripts/project.py check
python scripts/project.py stop
python scripts/project.py up
python scripts/project.py upgrade-plan --source D:/AdminCore --ref HEAD
```

`stop` 保留全部数据卷；`up` 继续使用原库，管理员引导命令不重置已有密码。所有运维动作先核对容器、卷、网络的项目名和随机实例标签，遇到同名异属资源直接拒绝。不要删除 `admincore.project.json` 或手工伪造实例标识。启动失败保留新项目、卷和 `.codex-validation/project-start.log`，不会自动删库回滚。

## 升级方法

1. 先在新项目建立自己的 Git 仓库，提交源码、锁文件和 `admincore.project.json`；保留业务分支，环境和数据不入 Git。
2. 审核目标底座提交的 CHANGELOG、锁文件、模块/API 契约和迁移说明。运行 `upgrade-plan` 得到原始导出、当前业务副本、目标底座三方摘要；输出只有路径和冲突标记，不含文件内容或环境值。该命令只读，不执行合并、迁移、重建或修改基线。
3. 使用下面的受控源码升级命令应用计划。无冲突源码可以更新；冲突路径必须明确保留本地或采用上游，工具不猜测业务语义，不自动进行文本合并。也可以先用 Git 三方合并手工处理，重新生成计划后应用。不要把目标 `.env`、随机实例标签、Compose 项目名或元数据直接覆盖到业务项目。
4. 在隔离项目先执行锁文件检查、后端/前端测试、严格 OpenAPI、迁移计划、空库初始化、存量升级及模块启停验证；变更依赖时按锁轮转文档处理，不直接浮动安装。
5. 正式环境停写，生成并校验数据库与媒体备份，完成恢复演练，再执行构建和正向迁移。以业务数据计数/摘要、健康探针、授权与关键业务验收决定放行。
6. 使用 `upgrade-accept` 执行项目明确登记的验收命令；全部成功后才推进元数据中的上游基线。保留本地的冲突会成为相对新基线的业务差异，下一轮仍能识别。升级记录、源码备份及验证日志归档到 `.codex-validation/project-upgrades/<id>/`，不要提交该私有目录。

### 受控应用与连续升级

先确保业务项目自己的源码已提交且当前没有其他程序同时写源码。已有项目需要先移植这一版 `scripts/create_project.py`、`scripts/project.py`、`scripts/project_upgrade.py`，并在项目 `.gitignore` 加入 `.admincore-upgrade/`、`.admincore-upgrade.lock` 和 `.codex-validation/`；原始 `admincore.project.json` 保留。

```powershell
$targetRef = '替换为已审核的目标SHA或标签'
python scripts/project.py upgrade-plan --source D:/AdminCore --ref $targetRef --output .codex-validation/upgrade-plan.json
python scripts/project.py upgrade-apply --source D:/AdminCore --plan .codex-validation/upgrade-plan.json
```

计划文件必须由操作者保存并审核。应用时重新核对原始元数据、目标 SHA 和本地文件摘要；计划过期、链接/junction、目录冲突、Windows 大小写/保留名冲突均拒绝。冲突用重复的 `--keep-local 路径` 或 `--take-upstream 路径` 明确决策；计划中的源码删除另外要求 `--allow-delete`。新文件与业务已有文件同名也按冲突处理。工具既不删除业务数据库、媒体和卷，也不运行上游提供的命令。

应用后原始基线不变，备份与中断日志保留于 `.admincore-upgrade/`。操作者编写一个私有 JSON 验收文件，其中每一项都是命令的 argv 数组，例如：

```json
[
  ["python", "scripts/check_dependency_locks.py"],
  ["docker", "compose", "exec", "-T", "backend", "python", "manage.py", "check"]
]
```

这只是命令格式示例。实际项目应使用对应项目名、预设和覆盖文件的 Compose 命令，并登记自己的后端测试、前端构建、迁移检查和业务验收。Windows 的 npm 命令可用 `node` 加 npm CLI 的绝对路径，避免依赖 shell 执行 `.cmd`。验收文件是操作者本地信任的可执行配置，不能直接使用下载的模板。命令以项目根目录为 cwd，`shell=False`，每项最多 20 分钟，失败或超时不推进基线；日志可能包含项目输出，应按私有资料保管。

```powershell
python scripts/project.py upgrade-accept --checks .codex-validation/upgrade-checks.json
# 尚未验收且需要撤回本次源码应用：
python scripts/project.py upgrade-restore
```

源码再次变化时，验收和恢复会拒绝覆盖，需先人工核对。恢复只涉及本次应用文件，保留无关业务文件；已经验收的版本不能用此命令回退。进程被强制终止可能遗留锁，必须先确认锁中 PID 已退出才能人工移除锁，再恢复或重试验收。该机制不替代数据库备份、正向迁移或发布验收，也不能把一个空命令的成功等同于真实业务验收。

此流程提供可审查的修复同步方法，不承诺自动无冲突升级任意二开项目。禁止通过 `down -v` 或反向删除迁移实现回退。仅在已证明数据库结构兼容时回退代码；不兼容迁移需停写并恢复完整备份，恢复点之后的业务写入可能损失，须按项目恢复目标单独决策。

### 可复现的真实 Django 连续升级验收

使用项目锁文件对应的 Python 环境执行，证据目录必须尚不存在：

```powershell
backend/venv/Scripts/python.exe scripts/validate_project_upgrades.py --output .codex-validation/project-upgrades-django-local
```

Linux/CI 使用 `python` 替换解释器路径。脚本只创建自己的临时 Git 上游和独立业务副本，不读取实际 `.env`、不改主仓 Git/底座版本、不启动服务、不连接生产数据库。它复用实际的创建、计划、应用和验收工具，用最小 Django 底座的 A、B、C 三个真实提交验证两轮完整升级。下游自有业务 app 使用独立 SQLite 数据库，三条订单同时关联真实 `auth.User` 与底座实体；迁移依赖使用 `swappable_dependency(settings.AUTH_USER_MODEL)`。

每轮增加一个底座字段并执行 `RunPython` 存量回填，`upgrade-accept` 内实际运行 `migrate --noinput`、`check`、`makemigrations --check --dry-run` 和业务数据检查。用户、实体原有字段、订单及其外键的摘要必须保持一致，新增字段另行核对预期回填值；同时核对业务源码、`.env`、Compose 实例标签与 `instance_id` 均未改变。应用后基线必须仍为旧 SHA，全部检查通过后才能前进；第一轮特意在迁移之后注入一个失败验收，确认即使数据库已迁移，基线仍不被提前接受，随后可重新验收。

证据目录保存无凭据 `report.json`、命令输出和两轮迁移验收日志。成功后删除本次创建的临时上游、业务副本和数据库；失败则保留隔离工作区位置及日志，可能含随机 `.env`，应作为私有排障资料。无后台 PID 或端口需要停止。CI 的 `project-template` 作业已包含该检查和报告归档。

2026-10-19 本地验收使用 Django 5.2.18，两轮均通过；一个用户、三个底座实体和三条订单的业务摘要保持一致，两次新增迁移均真实执行，失败检查未推进基线，脚本自己的成功工作区已清理。创建/升级/真实 Django 集成测试共 54 项通过；Windows 运行这些测试时设置 `PYTHONUTF8=1`，避免旧测试的 Git 中文输出按系统 GBK 解码。该结果证明通用升级工具对真实 Django 存量迁移的闭环；夹具是最小 Django 项目，不等同于全量 AdminCore 发布升级、任意业务迁移兼容性或 PostgreSQL 生产迁移验收，真实业务项目仍须执行前述隔离验证和备份恢复流程。

## 版本及兼容规则

采用语义化版本：开发阶段使用 `0.x` 与预发布标识；发布时必须同步本文件说明、CHANGELOG、唯一版本文件和验收 SHA。补丁为兼容修复，次版本为兼容新增；破坏性契约更改需主版本和明确迁移指引，不能以升级依赖替代评估。

API 废弃遵守已有至少 90 天兼容窗口与替代/迁移说明，见 API 生命周期文档；模块契约新增可选字段保留版本，删改语义需新契约及调用方验证。数据库采用先加后迁再移除，关闭模块仍保留 app/迁移/历史数据；无法满足兼容窗口的安全修复需单独公告范围和处置，不静默改旧行为。
