# AdminCore 部署指南

## 固定运行环境

版本基线见 [版本要求](../版本要求.md)。镜像固定为 Python 3.13.15-slim、Node 24.21.0-slim、Nginx 1.29.8-alpine、PostgreSQL 18.6、Redis 8.10.2。依赖通过 `requirements.lock` 哈希安装及 `npm ci` 安装；前端构建复制 `.npmrc` 校验运行时。

Nginx 托管 SPA，`/api/`、`/admin/`、`/static/` 代理 Django，`/media/` 返回 404。文件使用带认证的下载 API。应用默认上传上限 50 MiB，Nginx 请求体上限 52 MiB。

## 首次部署

脚本使用 Bash；Windows 在可调用 Docker Compose 的 WSL 或 Git Bash 中执行。

```bash
cp .env.example .env
# 编辑 .env：设置至少 50 字符的随机 DJANGO_SECRET_KEY、强 DB_PASSWORD、ADMINCORE_ADMIN_PASSWORD
# 按实际域名设置 DJANGO_ALLOWED_HOSTS
docker compose up -d --build
bash scripts/health_check.sh
```

后端先迁移，再初始化权限、角色、菜单和管理员；worker/beat 只迁移，不创建账号。首次管理员必须明确提供强密码。生产环境拒绝 `--demo` 和公开演示密码，不打印密码，不默认创建 demo。

已有环境升级前，通过原环境的 `python manage.py changepassword admin` 轮换公开默认管理员密码，并禁用不再需要的演示账号。初始化命令发现管理员仍使用公开默认密码会阻止启动。升级包含用户会话版本、菜单排序及 SimpleJWT 黑名单表迁移；旧令牌失效，用户需要重新登录。退出登录撤销该用户全部现有会话；修改或重置密码也撤销旧凭据。

升级前备份并校验数据库和媒体；构建时包含 `backend worker beat frontend` 四个服务，随后执行 `docker compose up -d --wait` 和 `docker compose exec -T backend python manage.py migrate --check`。`beat` 使用独立镜像，不能遗漏。已有 PostgreSQL 卷不会因修改 `.env` 自动更新角色密码，轮换数据库凭据时必须同步修改数据库角色和应用配置。

公开注册默认关闭（`ALLOW_PUBLIC_REGISTRATION=False`），由管理员创建用户；明确需要自助注册时再开启。`ADMINCORE_ADMIN_PASSWORD` 只用于新账号初始化，不会覆盖已有管理员密码。

生产配置拒绝缺失、过短、重复度过高和已知示例密钥。构建时 collectstatic 使用仅在该进程存在的随机临时密钥；运行时必须提供独立密钥。

## HTTPS 网关

前置网关终结 TLS 时设置 `USE_TLS=True`，将 `TRUSTED_PROXY_IP` 设置为直接连接 Nginx 的网关 IP。网关必须覆盖客户端的 `X-Forwarded-Proto`。Nginx 仅接受该来源的 https 协议头，其余来源按实际连接协议处理。默认 127.0.0.1 不信任外部来源。

TLS 环境通过 HTTPS 地址检查；内部后端探针通过 `docker/healthcheck.py` 自动适配 TLS 标头与允许的主机名。后端的 `SECURE_PROXY_SSL_HEADER` 依赖可信代理边界，8000 端口应仅供内部使用。Compose 端口映射可按部署边界限制。

Compose 默认将 8000 绑定到 `127.0.0.1`。Nginx 仅从 `TRUSTED_PROXY_IP` 接受客户端地址与协议，覆盖后端的 `X-Forwarded-For`；Compose 对 DRF 配置单层代理，独立后端默认只使用直连地址（`DRF_NUM_PROXIES=0`）。不要把后端绑定到公网后继续信任任意来源的转发头。

登录采用 Redis 原子计数的固定 60 秒时间窗：同一来源最多 10 次、同一用户名最多 5 次，失败响应为 429 并返回 Retry-After。窗口边界可能出现相邻两窗的请求，不能把它当作抗拒绝服务保障。API 的原有匿名/用户限流仍保留。

SPA 页面与带哈希静态资源发送 CSP，拒绝内联脚本和 eval；动态组件样式允许 inline style。后台文档与 Django admin 使用不同脚本机制，不套用 SPA CSP。SPA HTML 使用 no-cache，带哈希资源保留长缓存。`SECURE_HSTS_SECONDS` 默认 0，仅在 `USE_TLS=True` 且实际 HTTPS 域名验收后逐步增加。

## API 契约与 CI

Schema、Swagger 和 ReDoc 入口保持在 `/api/v1/`，仅管理员可访问。补齐自定义 JWT、安全声明、响应包、分页结构、请求字段、UUID 参数和下载格式。构建后的严格契约验收命令：

```bash
docker compose exec -T backend python manage.py spectacular --validate --fail-on-warn --file /tmp/admincore-schema.yml
```

GitHub Actions 执行固定 Python/Node/npm 版本的后端测试、严格 schema 校验和前端 lint/类型/构建检查。CI 结果须以实际运行结果为准，配置文件存在不等于远端已通过。

## 定时任务

Beat 使用数据库调度器，后端启动的 `bootstrap_admincore` 会自动录入缺失的四项维护计划。已有计划的时间和启停状态保持不变。也可独立补录：

```bash
docker compose exec -T backend python manage.py configure_maintenance
```

北京时间 03:00 清理软删除超过 30 天的文件，03:15 清理已读超过 90 天的通知，03:30 清理过期幂等记录；未读通知保留。可靠事件每分钟补偿派发，失败指数退避。保留期通过 `.env` 的 `FILE_SOFT_DELETE_RETENTION_DAYS`、`NOTIFICATION_RETENTION_DAYS` 调整。录入命令不会立即执行清理，时间及启停可在 Django Admin 的 Periodic Tasks 中调整。建议每日运行 `python manage.py flushexpiredtokens` 清理过期黑名单。

管理员可在“可靠事件”页面查看状态、尝试次数和脱敏错误类别，修复原因后重新派发失败事件。该操作记录审计，页面与 API 都限制为管理员。升级应一起重建 worker 和 beat，使任务注册与维护计划一致。

默认菜单只在新空库初始化一次，已有库保留当前菜单。修改、隐藏、删除菜单后，重启不会恢复默认值。升级先备份，随后执行 `docker compose build backend worker beat frontend` 和 `docker compose up -d --wait`，入口自动应用迁移。

## 备份与恢复

媒体默认使用本地卷，也支持部署选择 S3 协议后端；配置、停写复制迁移、私有访问及对象恢复边界见 [存储适配与验收](存储适配与验收-2026-10-13.md)。切换模式不会自动迁移旧文件。

```bash
bash scripts/backup.sh                   # 自动时间戳，输出恢复命令
bash scripts/restore.sh 20261013-120000   # 使用实际备份时间戳，输入 yes
bash scripts/health_check.sh
```

备份暂停应用写入方，生成 `backups/admincore-db-<时间戳>.dump`（PostgreSQL custom format）、媒体 `.tar.gz` 及 `.sha256` 清单，结束时恢复原先运行的服务。失败留下 `.partial`，不能作为完整备份。可设置 `BACKUP_DIR`；自动执行器使用可迁移目录的 basename 校验清单。人工备份/恢复与自动执行器共享宿主锁，Windows 使用 Git Bash（`ADMINCORE_BASH`）和现有 Python（`ADMINCORE_PYTHON`）。自动计划默认关闭，配置及 RPO/RTO、密钥保管/演练要求见[自动备份与恢复目标](自动备份与恢复目标-2026-10-14.md)。

恢复先验证固定文件校验和、完整导入独立 staging 数据库并检查迁移表、检查媒体归档路径，然后停写切换数据库和媒体。数据库改名使用事务；不会删除媒体卷挂载目录。切换后的健康检查失败会自动回滚；回滚本身失败则保持应用停止并保留现场。可设置 `FRONTEND_URL=https://实际域名` 指定检查地址。

成功后保留旧库和旧媒体，名称与路径见脚本输出；业务验收后由运维明确清理。备份排除媒体 staging 副本。备份应另存异地；跨 PostgreSQL 大版本迁移另行演练。

旧 `.sql.gz` 不能直接使用新脚本恢复。在隔离的空数据库中执行 `gzip -dc old.sql.gz | psql -X -v ON_ERROR_STOP=1 ...`，成功后用 `pg_dump -Fc` 导出；配对当时的媒体归档，为两份固定文件用 `sha256sum` 生成清单。禁止向在用数据库直接灌入旧 SQL。

## 日常检查

```bash
docker compose logs -f backend worker
docker compose exec backend python manage.py migrate --check
bash scripts/health_check.sh
```

健康 API 实际检查数据库查询和 Redis ping，依赖失败时返回 503 且不暴露连接细节；健康脚本检查 `status: ok` 和独立 worker ping，避免将 SPA 的 HTTP 200 当作后端健康。worker 不作为 backend 探针的依赖，避免与 Compose 的启动依赖形成循环。权限按动作在后端校验；菜单和按钮配合授权。导入取消逐行协作停止，已完成的行保留。

本次验收结果与尚未覆盖的环境见 [兼容性记录](../COMPATIBILITY.md) 和 [修复验收报告](修复验收报告-2026-10-13.md)。
