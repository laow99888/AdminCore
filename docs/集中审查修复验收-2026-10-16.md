## 行为与运维注意事项

- 永久删除接口返回 **202、已提交永久删除任务**，只表示记录删除和清理意图已经提交。物理对象尚可能存在，worker 会重试失败清理；需要运行可靠事件调度并监控 `file.purge`。生命周期清理结果中的 `purged_files` 保留兼容字段，计数指逻辑记录移除，不代表存储已即时擦除。存储配置改变时清理任务拒绝操作，需核对存储归属后处理。
- 外部发送前再次核对授权并提交发送快照。发送已经开始后，数据库无法撤回外部系统已接受的消息。超时后的 `notification.delivery` 不确定结果标为终止，防止重复发送；非幂等第三方系统不能承诺严格 exactly-once。
- `ADMINCORE_TRUSTED_PROXIES` 必须配置为实际直接代理的 CIDR。默认不信任转发头；不能随意填所有地址或整个不受控网络。通用 DRF throttle 的代理配置是另一层机制。
- `DJANGO_ENV=development` 是本地开发的显式选择。生产镜像和 Compose 使用 production；测试使用 testing，并通过 `PYTHON_DOTENV_DISABLED=1` 避免读取本地凭据。
- Windows 上的 POSIX mode 不等价于 ACL；部署者仍需为备份父目录配置专用账户 ACL。现有未知宽权限路径会拒绝写入，修复工具不会擅自改其权限。
- 本轮增加 Outbox `processing`、MessageDelivery `sending` 两个迁移。上线须按版本执行迁移，并让后端、worker、beat 使用同一次构建。

22 项缺陷的实现与 R1～R9 的长期工程建议分开统计。本轮已将核心缺陷变为正式回归，并将真实 PostgreSQL 检查纳入 CI、补 CI 最小权限与超时、共享 API 地址等。**尚未完成**：R1 扩大全业务覆盖率基线、R2 定期漏洞扫描、R3 HttpOnly/BFF 迁移评估及实施、R4 开发依赖拆分/非 root/静态门槛、R5 目标容量验证与完整保留矩阵、R6 全面类型和样式整理、R7 全角色构件与健康恢复体系、R8 全端点授权契约目录、R9 按入口约定请求幂等及旧代码整理。
