# 历史清理与审计保留

本批提供三类数据库日志和新登记导入源文件的保留策略、默认关闭的注册清理计划、有界执行和失败记录。运行日志改由 Compose 容量轮转。导出当前仅生成响应内容，不在服务器建立持久化导出目录；未知目录和旧版导入文件不会按名称猜测删除。

| 交付字段 | 本批范围 |
|---|---|
| 功能范围 | 定时维护中的“清理历史日志与导入源文件”；预览/确认、保留参数、分批删除、任务结果、逐批摘要审计；精简部署的终端入口 |
| 默认是否启用 | 新计划默认禁用，Asia/Shanghai 04:00；重复初始化保留已修改计划。控制台日志默认启用，Compose 每容器 10 MiB × 3 轮转 |
| 外部依赖 | 页面依赖 tasks，异步执行依赖 worker/beat/数据库；导入源使用当前本地或 S3 存储。CLI 不要求 Redis/worker，不访问任意路径 |
| 权限与数据范围 | 维护页面须管理员及 schedule:read/update/run；参数沿用 config:read/update；worker 重新检查发起人及会话。查看日志沿用 log:read 与 log 数据范围。定时任务及受信任 CLI 为全局运维清理，不按当前页面筛选执行 |
| 关闭后的行为 | 禁用计划停止后续自动登记；已提交或运行中的手动任务仍按既有规则处理。tasks 关闭不加载页面及消费者；data_io 关闭保留所有导入源，日志清理不受其影响；CLI 为受信任运维入口，默认仅预览 |
| 可重复验收 | 后端生命周期测试；Playwright 定时维护桌面/手机用例；validate_storage 的真实 MinIO；validate_foundation 的真实 PostgreSQL/本地对象及双向行锁竞争。证据和部署记录见末尾 |

## 保留与归属

| 资源 | 默认保留/归属 | 删除与失败处理 |
|---|---|---|
| OperationLog | 365 天；lifecycle.operation_days，最低 180 天，最高 3650 天 | 每批 100 条，每次最多 1000 条；同事务先记清理摘要再删，失败回滚该批，前面已完成批次保留 |
| LoginLog | 180 天；lifecycle.login_days，最低 30 天 | 同上；不以用户名选择性清理 |
| ExceptionLog | 90 天；lifecycle.exception_days，最低 7 天 | 同上；不把堆栈或错误私密正文复制进清理结果 |
| 新登记导入源 | 30 天；lifecycle.import_days，最低 1 天，最高 3650 天；由上传用户与导入 TaskRecord 关联 | 仅 purpose=import、未软删且超过期限。任一等待/运行任务、完成时间未知或最近使用的任务保护源文件。最多处理 1000 个可删除源；锁后复核，存储失败保留记录并可见 |
| 旧版导入源 | 升级不修改已有 purpose=general 数据 | 不自动删除；管理员识别后按原普通文件生命周期管理，不能批量猜测归属 |
| 普通文件与历史头像 | 既有 files.retention_days，默认软删后 30 天 | 继续使用独立注册清理计划、预览、最终删除审计及存储失败处理；当前使用的头像受引用保护 |
| 已读站内通知 | 既有 notifications.retention_days，默认 90 天 | 原通知清理计划；未读保留。公告不是逐人通知，不参与该清理 |
| 会话/邮件挑战/JWT 记录 | 失效或撤销后至少 30 天；验证码挑战/守卫过期至少 1 天 | 核心会话清理入口有界执行，不触碰有效会话；精简部署由运维执行 |
| 幂等结果 | 记录自身 expires_at | 核心计划只清已成功且过期记录，业务资源不随之删除 |
| 业务记录、TaskRecord、OutboxEvent | 默认持久保留，避免任务重试/事件去重证据断裂 | 无本批自动删除；业务资源另行登记策略，不能以日志期限套用 |
| 导出 CSV/XLSX、导入模板、预览/头像中间内容 | 请求范围内生成和释放，当前无持久导出产物表或下载链接 | 内存行数/字节数限额沿用已有规则。Django 上传临时文件由请求关闭；媒体复制/备份上传使用上下文临时文件。异常中间产物/宿主未知临时目录不做全盘扫描；新增持久化产物须注册归属/期限/失败处理 |
| 应用及 Nginx/数据库/Redis/Celery 运行日志 | Compose json-file，每容器 10 MiB × 3；容量上限而非天数承诺 | Docker 自动轮转；本批切换需重建容器。原 logs 卷及历史文件保留，不自动清空 |
| 可选宿主文件日志 | DJANGO_FILE_LOGGING=True，单进程使用 10 MiB × 11 | 默认 False，多进程禁止共享同一 RotatingFileHandler 目标；宿主自行配置平台轮转 |
| 备份完整集及失败产物 | 既有独立备份策略，默认 30 天且至少 7 份 | 仅成功且重新校验的完整集自动回收；失败/partial 保留，见自动备份验收 |

清理总预算 180 秒，Celery 270/300 秒软/硬限制。达到条数或时间预算时 more=true，提示重新预览；定时下一轮继续。受保护源先从候选集合排除，避免最旧的长期任务阻塞后续文件。各资源计数为执行时读数，不承诺跨所有表的同一快照。

## 使用

先在“系统参数”设置四项 lifecycle.*_days，再到“定时维护”运行预览。实际执行需当前操作者 15 分钟内的成功预览及“执行清理”确认；策略或模块变化会使预览失效。实际执行重新按期限选择对象，期间新增的过期记录也可能被处理。

精简部署可在受信任终端使用：

```powershell
python manage.py cleanup_history
# 默认只预览；实际清理须精确确认，作用于当前连接的数据库。
python manage.py cleanup_history --execute --confirm 执行清理
```

参数只允许 dry_run；没有文件路径、模型名、SQL、任意函数或删除天数的网页参数。保留参数须通过白名单系统参数改动并审计，不能用清理请求绕过最低期限。

导入重试先取得同一源文件行锁，再登记新任务。清理先完成时重试返回明确 400，要求重新上传；重试先登记时清理在锁后看到 pending 任务并保留文件。源文件已清理不删除历史任务结果。

文件删除失败使任务为 failed/lifecycle_partial_failure；显示各类已删数量与最多 20 个失败文件 ID/固定错误码，不包含私有存储地址或异常正文。重试应检查存储后重新预览，已开始的破坏性任务禁止直接重放。存储与数据库不能成为一个原子事务：若对象删除后进程/数据库提交失败，数据库可能保留缺失对象记录，须核对备份恢复或重新清理，不宣称跨系统回滚。

本批摘要只包含任务 ID、类别、对象 ID 和数量。完整关键变更前后值与请求串联仍是下一项审计工作，不以此摘要替代。
