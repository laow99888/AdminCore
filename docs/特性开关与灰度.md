# 特性开关与灰度

这是可选模块，默认关闭。适用于逐步投放业务功能；权限、数据范围和登录安全检查仍由业务接口执行。

## 启用与授权

使用完整构建，在部署配置的 `ADMINCORE_MODULES` 中加入 `feature_flags`（保留项目所需的其他模块），执行数据库迁移及 `python manage.py bootstrap_admincore` 后重启服务。后端源码仍保留迁移，关闭模块不会删除数据。精简构建不包含管理页面，不支持通过运行时配置加入可选模块。

系统管理 → 特性开关提供搜索、分页、新增、编辑、删除。权限分别为 `feature_flag:read/create/update/delete`；已有普通角色不会自动获得新权限。只有查看权限时不显示写入操作。查看权限还允许搜索最多 50 个匹配的用户/角色名称及其标识，供投放名单选择，不包含邮箱、电话等资料。

## 规则

开关标识以小写字母开头，可使用字母、数字、点、横线、下划线，最长 100 字符；创建后不可修改。新建开关默认关闭，比例为 0%。比例按万分位保存，界面支持百分比的两位小数。

先判断模块、身份和开关是否启用，再判断排除名单；排除用户永远不会命中。其余用户只要命中包含用户、有效角色、稳定比例中的任意一项便命中。每类名单最多 100 个目标。停用用户、强制改密用户及已撤销的角色关系不会因旧规则继续命中。

比例通过开关独立随机种子和用户 UUID 的哈希计算。扩大比例时，原来命中的用户继续命中；修改名称、名单不会重新随机分组。100% 包含全部有效用户（排除名单仍优先）。删除后判定关闭；以同一标识重新创建会产生新的种子。

## 业务接入

后端在业务权限检查后、执行功能前调用：

```python
from apps.feature_flags.services import feature_enabled

if feature_enabled('orders.review', request.user):
    # 执行已获授权的新功能
    ...
```

前端通过 `featureFlagsApi.evaluate(['orders.review'])` 调用 `POST /api/v1/feature-flags/evaluate/`。只能判断当前登录身份，不能传入其他用户；每次最多 100 个不重复标识。返回 `[{"key": "orders.review", "enabled": false}]`，不能将判断结果当作授权凭证。不存在的标识按关闭处理；模块关闭时 API 返回 404，接入方应按关闭处理。后端 helper 在模块关闭时返回 False 且不查询开关表。

管理接口位于 `/api/v1/feature-flags/flags/`。创建需 `version: 0`，支持 `Idempotency-Key`；编辑/删除必须提交最近读取到的 `version`，并发变化返回 409。界面保留输入并要求先查看差异再明确载入服务端版本。写入时再次检查当前身份、设备会话、权限，审计失败则回滚；响应禁止缓存。

规则直接从数据库读取，不使用跨请求结果缓存，因此关闭和撤权在下一次判定时生效；已经开始的业务操作不被自动撤销。

## 验收

可运行 `python scripts/validate_feature_flags.py`，在独立 PostgreSQL 中执行实际迁移及规则、撤权、幂等、审计回滚和双连接并发验收。该脚本成功后移除自己创建的容器；失败保留日志和容器，见输出报告。前端专项为 `feature-flags-contract.test.ts`、`feature-flags-view.test.ts`、`e2e/feature-flags.spec.ts`。

原 P2 批次结果见 [P2 执行与验收记录](P2执行与验收记录-2026-10-16.md)，当时尚未部署到公网。后续产品提交的 CI 和部署证据从 [兼容性记录](../COMPATIBILITY.md) 查询；代码随发布存在不代表具体环境已经启用灰度模块或配置业务规则。
