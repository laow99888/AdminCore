# 用户批量结果与事务边界

`POST /api/v1/users/bulk_action/` 现在返回明确的整批事务标记、成功/失败数及逐项结果。启用、停用和删除仍整批成功或整批回滚；响应与审计沿用原始提交顺序，数据库锁定继续按主键排序，避免反序请求造成锁序相反。

| 项目 | 当前契约 |
|---|---|
| 输入 | 原 `action` 与 `user_ids` 不变，1至1,000个UUID |
| 权限 | 保留 `user:update`，删除另外要求 `user:delete`；仍复核数据范围与管理员账号保护 |
| 返回 | `data.atomic=true`、`succeeded`、`failed`、`results: [{id, status}]` |
| 成功 | HTTP 200，各项status为200；计数代表已处理的输入项，不代表实际字段值发生变化的数量 |
| 拒绝 | 重复、缺失或不可访问对象整批403；各项统一403，不指出哪个ID存在或有权限 |
| 回滚/故障 | 受保护业务引用整批409；业务/审计故障整批500，均不报告成功项，不暴露关联或异常详情 |
| 输入/认证失败 | 参数非法仍400及字段错误；认证/中间件先行拒绝仍保持原响应，不保证逐项结果 |
| 依赖/启停 | 核心用户入口，无新依赖、迁移或默认开启的可选能力；精简预设仍可使用 |

返回示例：

```json
{
  "code": 200,
  "message": "deactivate success",
  "data": {
    "atomic": true,
    "succeeded": 1,
    "failed": 0,
    "results": [{"id": "00000000-0000-4000-8000-000000000001", "status": 200}]
  }
}
```

顶层HTTP状态及消息保持；成功/已解析的业务拒绝原先返回 `data:null`，现在返回上述结果对象。自定义客户端如显式要求null，需按OpenAPI更新；仓库客户端已增加结果类型。失败项的status描述整批结论，不能理解成逐项独立执行。前端统一错误拦截仍保留原错误行为。

事务内异常会整体回滚；500或网络断开不构成自动重试许可。若数据库提交确认或HTTP响应丢失，客户端应重新查询状态后决定后续操作；本接口尚未提供幂等键，不宣称网络故障下恰好执行一次。

文件回收站的批量操作按项独立事务、显式部分成功，接口已有 `results/succeeded/failed/dry_run`，本批未改成用户的整批规则。异步导入继续使用已有逐行SQL账本及权限复核。
