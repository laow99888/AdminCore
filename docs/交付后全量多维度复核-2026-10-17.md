## 结论

基座已经部署，正常功能路径和工程流水线有较好的基础；但新增反例确认了权限、审批执行、数据校验和设计器交互缺陷，不能把此前“交付完成”理解为“已经没有重要问题”。尤其是 A01—A03，应该在依赖审批处理真实业务前优先修复。

本轮共 **17 项确认问题：P1 4 项、P2 12 项、P3 1 项**。其中 **14 项涉及当前启用功能或文档，3 项仅在开启多租户/只读副本时触发**。线上这两项开关均已实读确认关闭，条件问题不表示当前站点已受影响。没有发现已被利用的证据，本轮也没有开展生产攻击验证。

这里的 A01—A17 只是本轮审查编号；P1/P2/P3 表示缺陷优先级，与原功能清单的 P2 批次、旧 R1—R9 修复批次不是一回事。同一根因在三个设计器出现只计一项，表单三个校验反例合计一项。

## 当前启用范围的问题

### A01 · P1 · 无关账号可通过抄送入口读取及修改他人审批

- 位置：[approvals/views.py](../backend/apps/approvals/views.py)，`cc()`，约 387—408 行。
- 复现：合成普通账号没有该审批的任何参与关系，GET 详情返回 **404**；对相同 ID POST `cc/` 却返回 **200**，建立抄送关系，并返回包含原申请 `content` 的完整序列化内容。
- 根因：入口只验证操作者仍有效；直接按主键锁定申请，没有经参与人查询集或独立的对象授权校验。需要知道申请 UUID，但 UUID 不能替代授权。
- 影响：同一可见租户范围内，泄露审批正文、步骤等内容，并允许未授权抄送写入。没有将其扩大描述为已验证跨租户攻击。
- 建议：在事务中统一复核申请访问和抄送操作权限；未授权请求不返回内容、不产生抄送和动作记录。保留合法申请人/审批人等业务角色的明确规则。

### A02 · P1 · 转办没有撤销原有委托，旧代理仍能批准

- 位置：[approvals/views.py](../backend/apps/approvals/views.py)，`transfer()` 约 330 行，`_workflow_decide()` 约 143 行。
- 复现：A 将步骤委托 C，随后转办 B；两个操作均 **200**。C 之后仍可 `approve/`，返回 **200**，申请最终为 **approved**。
- 根因：转办仅更新 `assignee`，没有清除 `delegated_to`；决定入口继续接受受托人。
- 建议：定义转办后的完整授权集合，原子撤销旧委托并更新版本；覆盖旧委托人、原审批人、新审批人和迟到请求的组合用例。

### A03 · P1 · 已接受的流程图会静默丢弃一条审批分支

- 位置：[approvals/models.py](../backend/apps/approvals/models.py) `validate_flow_definition()`，以及 [approvals/views.py](../backend/apps/approvals/views.py) 约 84、113 行。
- 复现：配置 `start → A`、`start → B`，两者各连接 `end`；图校验通过，发布接口 **200**。实例仅产生 **B** 步骤，B 同意后申请 **approved**，A 步骤数 **0**。
- 根因：校验接受分支图，运行器却将边转为 `{from: to}`，同一源节点的前一条边被后一条覆盖。
- 建议：最小修复是只接受当前引擎真正支持的线性节点图，严格约束出入度、起止节点和所有终止路径；节点内多人会签/或签继续保留。若要支持图分支，应另行完整实现执行语义，不能让未支持的图发布成功。

### A04 · P2 · 下一节点审批人停用会导致流程推进 500

- 位置：[approvals/views.py](../backend/apps/approvals/views.py)，`_advance_workflow()` 约 126—136 行。
- 复现：A → B 流程已发起后停用 B，A 同意返回 **500**；事务回滚，申请和 A 的步骤仍为 pending。
- 根因：下一节点查询只保留活跃账号，没有完整校验审批人集合，随后直接访问 `users[0]`。多人节点还可能只保留部分审批人，实际签署要求发生变化。
- 建议：推进时验证完整审批人集合，返回可处理的业务冲突；明确管理员调整/转办策略，不能崩溃或悄悄减少必需审批人。

### A05 · P2 · 抄送成功后，收件人仍看不到申请

- 位置：[approvals/views.py](../backend/apps/approvals/views.py)，`get_queryset()` 约 48 行。
- 复现：合法审批人抄送一个无其他参与关系的账号，操作 **200**；该收件人访问详情仍 **404**。
- 根因：默认参与范围不包含 `cc_recipients`，也没有可用的抄送视图。
- 建议：在修复 A01 的前提下定义抄送只读范围，接入详情和可发现的收件列表；抄送身份不自动获得审批权。

### A06 · P2 · 已撤回申请仍可转办并改变审批人

- 位置：[approvals/views.py](../backend/apps/approvals/views.py)，`cancel()`、`transfer()`。
- 复现：申请人撤回 **200**，原审批人随后转办仍 **200**；申请保持 cancelled，但审批人被改为新账号。
- 根因：撤回未终结 pending 步骤；高级操作只判断步骤待处理，没有统一校验申请状态。加签、委托等同类操作也需补齐状态约束。
- 建议：在申请锁内校验状态机，撤回/驳回时终止未处理步骤；终态后的写动作返回一致的业务冲突，不改变审批数据。

### A07 · P2 · 表单记录详情遗漏读取权限

- 位置：[online_forms/views.py](../backend/apps/online_forms/views.py)，`OnlineFormRecordViewSet` 约 80—98 行。
- 复现：记录所有者没有 `online_form:record_read`，列表 **403**，直接访问自己的记录详情却 **200** 并返回数据。
- 影响边界：已验证的是操作权限绕过；查询集仍限制本人，未据此声称可以读取其他人的记录。
- 建议：通过统一 action 权限映射覆盖 list/retrieve；测试权限撤销后“已知详情 URL”仍应拒绝。

### A08 · P2 · 表单必填、默认值类型及日期校验不足

- 位置：[online_forms/validators.py](../backend/apps/online_forms/validators.py)，约 45—47、83—100 行。
- 三个反例均被接受：必填文本 `""`；number 字段默认值 `{"unexpected":"object"}`；日期 `2026-02-31`。
- 根因：必填主要检查键存在；默认值直接复制且补值时跳过字段校验；日期仅匹配字符串形状。
- 建议：统一字段值校验函数，定义空值语义、严格验证默认值及补值后的结果，用日历解析验证日期。保留 boolean false、number 0 等合法值。

### A09 · P2 · 三种设计器的草稿版本不能阻止旧内容覆盖

- 位置：[online_forms/views.py](../backend/apps/online_forms/views.py) `perform_update()`；[reports/views.py](../backend/apps/reports/views.py) `perform_update()`；[approvals/views.py](../backend/apps/approvals/views.py) `ApprovalFlowViewSet.update()`；对应设计序列化器。
- 复现：在线表单、报表、审批流程分别持有 version=1；先保存新内容，再提交仍标为 version=1 的旧内容，两次均 **200**，最终 version=3 且内容被旧提交覆盖。
- 这是模拟两个客户端持有同一版本的依次提交，不依赖 SQLite 并发锁行为。
- 根因：服务端只递增版本，未要求及比较客户端期望版本；前端保存请求也没有提交冲突控制字段。
- 建议：借用已有版本冲突契约，原子比较更新；旧版本 **409**，界面保留本地编辑并提供刷新/比较。发布与编辑还需补真实 PostgreSQL 竞争测试，不能仅检查版本号递增。

### A10 · P2 · 报表错误筛选值可以发布，执行时 500

- 位置：[reports/validators.py](../backend/apps/reports/validators.py) 筛选验证，以及 [reports/services.py](../backend/apps/reports/services.py) 构造 ORM 条件处。
- 复现：users 数据源 `is_active eq "not-a-boolean"`，创建 **201**、发布 **200**、运行 **500**。
- 根因：只校验字段/操作符白名单及值的大致形状，没有按字段类型校验值和操作符兼容性。
- 建议：定义数据源字段类型与允许操作符，设计阶段拒绝非法值；运行时对存量错误定义返回可理解的 400/409，而不是内部错误。

### A11 · P2 · 三个设计器直接发布会丢失未保存编辑

- 位置：[ApprovalFlowDesignerView.vue](../frontend/src/views/approvals/ApprovalFlowDesignerView.vue) `publishFlow()` 约 85 行；[OnlineFormDesignerView.vue](../frontend/src/views/onlineForms/OnlineFormDesignerView.vue) `publish()` 约 18 行；[ReportBuilderView.vue](../frontend/src/views/reports/ReportBuilderView.vue) `publish()` 约 86 行。
- 组件复现：打开已有草稿，修改名称为新值后点击发布；三个组件均只调用 publish，update 调用数 **0**，响应后名称恢复为旧值并进入已发布状态。
- 根因：仅没有 ID 的草稿会先保存；已有 ID 的脏草稿直接发布数据库旧值，随后响应覆盖编辑状态。
- 建议：统一脏状态管理；发布应保存并发布同一预期版本，或明确阻止未保存发布。切换行、新建、离页的未保存提示也应使用已有通用机制。

### A12 · P2 · 三个设计器超过 100 条后没有访问后续记录的入口

- 位置：上述三个组件的 `load()`，分别约 77、16、84 行。
- 组件复现：接口返回 total=101、第一页 100 条，三个组件都仅显示 **100** 条，没有分页控件，也没有发起后续页请求。
- 根因：固定请求 page_size=100，只保留 items、丢弃 pagination。
- 建议：接入现有分页/搜索组件；覆盖 0、1、100、101 条及翻页后编辑/发布定位，不增加后端分页上限来掩盖问题。

### A13 · P2 · 审批列表存在关联查询随行数线性增长

- 位置：[approvals/serializers.py](../backend/apps/approvals/serializers.py)，`get_steps()`、`get_cc_recipients()` 约 35—40 行；[approvals/views.py](../backend/apps/approvals/views.py) 列表查询集。
- 复现：相同申请人、相同数据集，通过真实 API 捕获 SQL；1 条结果 **6 次查询**，5 条结果 **18 次查询**，增加 4 条带来 12 次查询。
- 根因：查询集未预取 steps/cc，且 flow_name 所需 flow 也未 select_related；每条记录再查询关联对象。
- 建议：按序列化读取模式 select_related/prefetch_related，确保方法字段消费预取结果；增加查询数预算测试。这里确认的是查询形状，不把当前小数据集结果当成生产性能压测。

- 位置：[README.md](../README.md)，约 90 行。
- 实际已经有多级审批设计与执行代码，交付清单也记为完成；README 却仍称“多级审批仍按清单暂缓”。
- 建议：统一入口说明，注明已实现范围、可选关闭项和本轮待修缺陷，避免新开发者或审查模型依据不同文档得出相反结论。

## 可选配置启用前的问题

### A14 · P2 · 多租户用户首次登录缺少可行的租户选择引导

- 位置：[tenancy.py](../backend/apps/core/tenancy.py) `activate_for_user()` 约 70—76 行；[authentication.py](../backend/apps/auth_app/authentication.py)；[AppHeader.vue](../frontend/src/components/layout/AppHeader.vue) 及租户 store。
- 复现：一个普通账号属于两个活跃租户，无本地租户 ID；登录 **200**，`auth/me/` **400**，`organization/my-tenants/` 也 **400**；预先提供合法租户 ID 后 `auth/me/` **200**。
- 根因：认证阶段在任何业务入口前要求指定租户，连用于取得本人租户选项的接口也被拒绝；前端又先取用户资料后才显示页头选择器。
- 建议：明确租户无关的认证/本人租户目录引导流程；只返回本人合法选项，再选定租户访问业务。还需覆盖本地缓存的租户被移除后的恢复。
- **线上多租户关闭，本轮在隔离环境显式开启复现。**

### A15 · P1 · 复制延迟下已停用账号仍可能通过 GET 认证

- 位置：[db_router.py](../backend/config/db_router.py) `db_for_read()` 约 101 行；[authentication.py](../backend/apps/auth_app/authentication.py) `get_user()` 及 [sessions.py](../backend/apps/auth_app/sessions.py) 会话检查。
- 复现：将隔离内存主库复制到另一个独立内存库，模拟副本尚未同步；主库停用账号并触发现有撤销机制后，副本账号仍 active。排除登录后的短暂主库粘滞 cookie，启用副本，原 JWT GET `auth/me/` 仍 **200**；主库 active=false、副本 active=true。
- 根因：安全方法把认证用户、会话及其他安全相关读取一起路由到副本，撤销可以被旧数据延后。短暂粘滞窗口不覆盖其他客户端及到期后的请求。
- 建议：认证、会话有效性、账号状态、权限/租户成员等安全判定强制读取主库；明确业务数据允许的复制延迟。增加真实双库/复制延迟撤权测试，不能只测试路由返回的别名。
- **线上只读副本关闭；不能按已验证即时撤权的配置直接启用。**

### A16 · P2 · 副本故障在真实 HTTP 异常链中没有回退主库

- 位置：[db_routing_middleware.py](../backend/apps/core/db_routing_middleware.py)，约 42—51、60—69 行；[exceptions.py](../backend/apps/core/exceptions.py) 异常响应处理。
- 复现：隔离副本可用时 GET users **200**；通过数据库 execute wrapper 注入 `OperationalError` 后，同一真实 API 请求 **500**，无 `X-AdminCore-Read-Replica-Fallback`，没有返回主库正常结果。
- 根因：DRF 已把数据库异常转换为响应，中间件 `except DatabaseError` 没有捕获到异常；现有单元测试直接让假的 get_response 抛错，未验证框架完整异常链。
- 建议：在可确认安全重试的数据库调用边界实施回退，或设计显式可识别的失败协议；避免对所有 500 盲目重放。补充真实 HTTP 故障注入测试。
- **线上只读副本关闭，本轮没有中断真实数据库。**

## 整体代码评价与修复顺序

优点是模块开关、共享权限/范围契约、事务写入复核、设备会话、基础组件、锁文件和 CI 已形成体系，项目可以继续演进，不需要推倒重写。当前主要问题是新模块的自定义实现没有完整接入这些机制：例如 cc 自行取对象、记录读取只在 list 手工校验权限、设计器各自实现保存发布和分页。类似约束散落后，正常流程测试容易全绿，组合操作和权限反例却漏掉。
