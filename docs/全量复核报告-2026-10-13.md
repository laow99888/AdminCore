## Standards：工程、安全与运行可靠性

### S01 · P1 · 生产新库自动创建公开固定密码超级管理员

位置：[entrypoint.sh:20](../backend/docker/entrypoint.sh)、[bootstrap_admincore.py:15](../backend/apps/core/management/commands/bootstrap_admincore.py)、[bootstrap_admincore.py:73](../backend/apps/core/management/commands/bootstrap_admincore.py)。

生产容器入口无条件执行演示初始化，新库将创建固定密码的超级管理员；密码还输出到 stdout 和欢迎通知。注释声称支持环境覆盖，但实际常量没有读取环境变量。隔离库确认该账户具有 superuser 权限，硬编码密码有效，stdout 包含密码。已有 admin 不会在每次重启时被重置，风险是新库首次初始化及保留演示凭据的环境。

修复：生产初始化与演示数据分离，首次管理员凭据显式提供，缺失时拒绝创建；移除日志和通知中的密码。验收应覆盖生产新库启动、重复启动和不提供凭据的行为。

### S02 · P1 · 退出和改密没有撤销刷新凭据，旋转配置未执行

位置：[auth_app/views.py:79](../backend/apps/auth_app/views.py)、[views.py:100](../backend/apps/auth_app/views.py)、[views.py:132](../backend/apps/auth_app/views.py)、[base.py:181](../backend/config/settings/base.py)。

自定义刷新入口直接派生 access，未执行配置中的 refresh rotation/blacklist；logout 仅返回成功，改密仅保存密码。复现退出及改密后旧 access 的 me 请求仍为 200，旧 refresh 可重复换取 access，且没有返回轮换后的 refresh。旧 access 的短期存活本身可由 JWT 策略决定，但旧 refresh 在退出和改密后继续使用一整天，会使撤销登录失效。有效期仍受原令牌限制，并非永久有效。

修复：明确退出、改密、管理员重置密码的撤销策略，接入真实旋转/黑名单或会话版本检查；测试旧 refresh、重放及并发刷新。

### S03 · P1 · 导入重试绕过管理员权限

位置：[data_io/views.py:90](../backend/apps/data_io/views.py)、[views.py:98](../backend/apps/data_io/views.py)。

任务 GET/POST 共用 IsAuthenticated；重试没有初次导入的 IsAdmin 检查。曾创建任务的管理员被降权后，初次导入为 403，但重试旧任务返回 200 并实际创建用户。修复时为写操作执行一致的授权检查，并确定 worker 对权限撤销的处理策略。上述结果已在隔离库复现。

### S04 · P1 · 数据库恢复不会按提示覆盖现有数据，SQL 出错也可能宣告成功

位置：[backup.sh:19](../scripts/backup.sh)、[restore.sh:20](../scripts/restore.sh)。

静态核对：备份为普通 pg_dump SQL，没有清理现有对象；恢复直接向运行中的同名数据库执行 psql，没有重建库、清空对象或 `ON_ERROR_STOP`。已有表和主键会产生冲突，备份之后的数据不会可靠消失，恢复过程中还可能部分成功；psql 默认 SQL 错误后继续处理，shell 的 `set -e` 不能替代 SQL 错误检查。文案“当前数据将被覆盖”因此不成立。

修复：先定义完整覆盖恢复流程，停写、检查归档、在隔离目标恢复并校验，显式检查 SQL 失败，再切换；至少设置错误即停。必须用有旧数据、备份后新增数据和故意坏 SQL 的隔离 PostgreSQL 验收。**本次未对用户数据库执行恢复。** [psql 官方错误处理说明](https://www.postgresql.org/docs/18/app-psql.html)。

### S05 · P1 · 媒体恢复删除卷挂载点，可能先删内容再失败

位置：[restore.sh:25](../scripts/restore.sh)、[docker-compose.yml:47](../docker-compose.yml)。

静态核对：`/app/media` 是命名卷挂载点，恢复先 `rm -rf /app/media`。删除挂载点通常以 busy 错误结束，但其内部文件可能已经删除；`set -e` 随即退出，后面的解压没有机会执行。缺少先验证媒体归档、失败回滚和停写步骤。

修复：不要删除挂载点；先在临时位置验证并恢复，设计保留旧内容的切换/回滚流程。坏归档、空归档和正常卷恢复必须在独立卷验收。**此项为代码/挂载配置推导，未运行删除命令。**

### S07 · P2 · 已取消的排队导入仍执行，并覆盖取消状态

### S08 · P2 · 审批决定缺少原子状态转换

位置：[approvals/views.py:80](../backend/apps/approvals/views.py)、[models.py:56](../backend/apps/approvals/models.py)。

### S12 · P2 · 入口上传上限只有 1 MiB，与后端 50 MiB 不一致

位置：[nginx.conf:22](../frontend/nginx.conf)、[base.py:131](../backend/config/settings/base.py)。
