## 3. 本轮新增确认的问题

### 3.1 生产密钥校验不足（上线前处理）

`backend/config/settings/production.py` 仅检查变量是否非空。隔离进程设置已知示例值后，生产配置仍导入成功，包含 `django-insecure-` 的开发默认值也被接受。

因此 Claude 所说“缺失变量时容器必然使用默认密钥”不成立：生产配置已拒绝缺失值。但“非空的示例或弱密钥可通过检查”成立，而且当前运行密钥已被 Django 部署检查明确报警。

建议在生产配置拒绝已知示例值和开发默认值，要求足够长的随机密钥；本地开发与测试配置保持可用。不能仅以字符串是否包含 `insecure` 判断随机性。

### 3.2 匿名限流可被伪造的代理头改变标识（上线前处理）

当前已配置匿名 `100/hour`、用户 `1000/hour`，缓存使用 Redis。问题不是“没有限流”，而是默认 `NUM_PROXIES=None`，前端 Nginx 又通过 `$proxy_add_x_forwarded_for` 保留客户端提供的转发链。

隔离复现：保持真实来源相同，仅改变客户端伪造的 `X-Forwarded-For` 左侧值，DRF 的限流标识就改变。设置与代理拓扑匹配的固定代理数量后，对照检查得到稳定标识。不能直接把固定数量 1 用于所有部署；应按实际入口覆盖不可信头并限制直接访问后端。

DRF 官方也说明内置限流依赖非原子缓存操作，不能独立承担强抗暴力破解或抗拒绝服务保障。参见 [DRF 限流文档](https://www.django-rest-framework.org/api-guide/throttling/)。应补登录专项保护和可信客户端地址回归。

### 3.3 OpenAPI 已启用，但契约生成不完整（持续开发前优先处理）

`backend/config/urls.py` 已提供 schema、Swagger、ReDoc，配置已启用 `AutoSchema`。因此 Claude 的“未集成 Swagger/OpenAPI”不成立。

本轮在隔离 SQLite 测试配置执行 `spectacular --validate --fail-on-warn`，退出码 1：91 次警告（31 种）、44 次错误诊断（6 种）。这些是重复诊断计数，不等于 44 个业务缺陷。主要问题：

- 认证、仪表盘、导入导出等视图缺响应/请求 serializer 注解。
- 自定义 `SessionJWTAuthentication` 缺 OpenAPI 认证扩展，生成器忽略认证定义。
- 部分 `get_queryset()` 未处理 `swagger_fake_view`，匿名 schema 请求触发 UUID 查询构造错误。
- 方法字段类型、UUID 路径参数、部分 operationId 不明确。

需要补契约注解和 schema 验证，再把产物与 CI 固定下来；只增加文档路由解决不了这些问题。

证据：[工作区 schema 校验日志](../.codex-validation/cross-review-20261013/workspace-schema-check.log)。

### 3.4 CSP 配置没有实际生效（安全加固时处理）

现有 `SECURE_CONTENT_SECURITY_POLICY` 字典没有对应生效机制。Django 5.2 不支持 Django 6.0 新增的内置 `SECURE_CSP`；不能把一个配置字典视为已发送 CSP。参见 [Django 6.0 CSP 设置](https://docs.djangoproject.com/en/6.0/ref/settings/#secure-csp)。实际在用响应也没有 CSP 标头。

前端真实地将 access/refresh token 存储在 `localStorage`，因此 XSS 防护值得加强。但这不证明已存在可利用的 XSS；迁移 HttpOnly Cookie 必须整体设计认证、CSRF、刷新与撤销协议，不能只替换登录视图。

### 3.5 健康检查范围有限（运维改进）

容器探针访问的健康端点只返回固定 JSON，未查询数据库或 Redis。因此后端的 healthy 状态不能独立证明依赖和业务正常。当前健康脚本额外检查 worker ping，Compose 也分别检查数据库和 Redis，不应说“完全没有依赖检查”。

改进时区分服务存活、依赖就绪及 worker 监控。worker/beat 等待 backend healthy，不能把 worker 在线作为 backend 的启动前置健康条件，否则可能形成启动依赖循环。

## 5. Claude 示例代码的适配与风险

| 示例 | 复核结果 |
|---|---|
| `LoginRateThrottle(SimpleRateThrottle)` 只指定 scope | 缺少 `get_cache_key()`，已隔离复现 `NotImplementedError`；不能直接用 |
| 重新赋值完整 `REST_FRAMEWORK` 字典 | 直接覆盖会丢失现有 JWT、分页、权限、过滤和统一异常配置；必须合并 |
| 新增 `UploadedFile` / 重写 User 模型 | 与现有 UUID User、FileModel 和数据关系不一致；不是增量修复 |
| `mimetypes.guess_type(file.name)` 防恶意内容 | 只由文件名推断，无法验证真实内容，也不等于病毒扫描 |
| HttpOnly 登录、Cookie 注入及只清 Cookie 的 logout | 返回协议不适配当前前端，令牌缺 `session_version`，丢失既有撤销逻辑；自动 Cookie 认证还要正确处理 CSRF |
| `/media/` 全局 public 缓存及 `response.content` 算 ETag | 违背当前私有媒体访问设计，流式响应没有普通 content；不能套用 |
| 用户/权限全局缓存 | 需要用户隔离、查询条件隔离及完整失效；示例用户名修改后旧缓存键仍可能残留 |
| `SERVE_INCLUDE_SCHEMA=False` 禁止公开文档 | 配置含义误读：仅让 schema 接口不出现在 schema 中，权限由 `SERVE_PERMISSIONS` 等控制；见 [官方设置](https://drf-spectacular.readthedocs.io/en/stable/settings.html) |
| Vue 测试片段 | `useUserStore` / `stores/user.ts` 不存在；ElButton 文本是 slot，不是 label prop；覆盖率插件和配置需按固定版本适配 |
| 类型提示片段 | User 并不位于其示例导入位置；DRF 类直接泛型化需对应运行时与 stub 支持，不能直接粘贴 |
| 前端 Dockerfile `npm ci --omit=dev` 后 build | 会去掉 Vite、TypeScript 等构建依赖，破坏构建；现有多阶段 Dockerfile 应保留 |
| 按需组件示例 | 仍调用未导入的 ElementPlus，且漏注册组件；并非可运行的完整替代方案 |
| Flower 配置 | 端口无认证，且应用模块、镜像命令参数、健康检查工具均未与镜像实际核对 |
| 缓存解析器及 Husky 安装片段 | 未按当前固定依赖核对 API 和可选依赖，不保证可执行 |
